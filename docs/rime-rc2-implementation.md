# 第二轮 Rime 体验版实施记录

## 范围与状态

用户已授权立即集中实现积压需求，完成针对性回归后制作正式包名、正式签名、非 Debug 的新体验版，继续实际使用测试。此前「体验期间只记录」的限制已结束，此次仍不创建标签或 GitHub Release。

本轮包含：

- 手动正常路径一次点击完成，与自动同步共用执行和安全恢复逻辑
- 可安全确认不兼容的记录自动留在 Rime，不逐批确认，不改编码或转写英文词库
- 更换存储位置时延续同步关系，不靠删除设备文件夹绕过冲突
- 词库状态的通俗文案、颜色与文字指示、Rime 状态及上次成功同步时间

**本轮工程回归已完成，正式签名体验包 `2.0.11-rc.2` 已覆盖安装。** 设备改为远程连接后，从当前源码重建隔离包并完成剩余回归，再安装已核验的正式产物。接下来由用户进行日常输入、视觉与长期自动同步体验，此次仍未发布。

## 第一批修改

同一设备目录、词典名称及协议版本下，存储 URI 不再被当作新的同步身份。迁移保留身份、盐、基线、仅保留在 Rime 的标记、代次及成功时间，自动同步不再因单纯选择另一位置而关闭。

选择新位置时读取本设备快照身份。已存在但不匹配的身份被拒绝，不保存该位置。新位置尚无本设备快照时保留原状态，已经成功同步过的关系不能在缺少该快照时将整份基线解释成删除，执行时返回明确错误，由已开启的自动同步延后重试。此检查只针对执行时可见的文件，不检测或等待外部同步软件。

尚未完成的事务仍禁止更换目录，沿用原先的安全限制。此阶段没有声称已经支持任意事务阶段的目录迁移。

## 新确认的统计问题

既有英文导出中的 28 条记录，其 `count` 字段之和为 42，与原生 `getDictionaryCount()` 返回值一致。这最初只是提示，不能单凭数值相等就确认接口语义。

随后在隔离包的未持久化中文词典副本中做了合成对照：

| 合成数据 | 导出记录数 | 记录权重之和 | `getDictionaryCount()` |
| --- | ---: | ---: | ---: |
| 一条记录，权重为 1 | 1 | 1 | 1 |
| 增加第二条记录，权重为 3 | 2 | 4 | 4 |

这确认该中文接口不能当作词条数使用，之前仅用全部权重为 1 的样本验证不足以证明计数口径。英文历史结果与权重求和一致，但本轮尚未追加独立的英文合成对照。

同步 Bridge 已改为使用本来就需要导出的数组长度计算记录数和容量预检，仍包括不可投影到 Rime 的原生记录，不新增全量导出。主机回归覆盖高权重不会误触发记录数上限，以及达到记录数上限时在写入前拒绝。

状态界面已移除错误的实时词条总数，使用该接口只判断可读取性。新增数量来自已提交的同步基线，明确标为「上次成功同步：双方共有……条，仅保留在 Rime 的有……条」。它只统计同步范围内的多字记录，不代表本机全部用户词典的实时词条数。没有为显示数字增加整份词库导出或 SAF 快照扫描。

- 从原始 APK 重建了隔离审计包，Compose release 编译和 API 31、33、34、35、36 静态门禁通过。
- 新源码通过 Rime 协议、原生 Bridge 主机回归、Java 编译及 Primary DEX Smali 检查。
- 隔离包通过生产 SQLite 状态 API 验证两次换位置：带相同身份及暂时没有快照身份，两次均保留身份、盐、代次、成功时间和 `RIME_ONLY` 标记。
- 隔离包验证外来身份被拒绝，已保存的位置不变。这是状态存储层验证，不是完整 SAF 目录迁移回归。
- 原生统计对照只使用合成数据和未持久化副本，没有访问正式词典正文。临时审计包与探针已卸载，没有创建公共存储临时文件，正式进程和默认输入法未变化。

## 集中实现

### 共用同步与兼容处理

手动和自动同步使用同一个执行入口。手动普通路径一次点击完成，只在首次接受处理规则或涉及删除时保留必要确认。普通中断后的未完成任务可通过「立即同步」接着处理，自动任务也走同一恢复路径。

排除记录需要先确认同一拒绝集合，再在未持久化的空副本中逐项验证拒绝，并检验已知可写入的合成对照记录。对照记录为「测试 / ce shi」，仅在临时副本中使用。验证成功后先恢复全部原有记录，再执行支持的变更及原有保存复核，对照不会被保存。全局插入故障、空副本中可接受的记录、对照无法导出或其他保存异常都不能自动归为不兼容。

此判定只表示当前原生词库无法直接接收该记录，不宣称拒绝原因一定是拼音错误。首次同意规则后自动处理后续符合条件的记录，不逐批询问，不改编码或转写英文词库。已有 `RIME_ONLY` 记录继续生效。旧版已开启的自动任务可继续处理普通同步，若首次遇到需要新规则授权的拒绝项，则暂停并提示确认。

### 状态展示

- 健康检查的 Java 已成为唯一实现来源，Smali 由现有生成器输出。旧设置页回调只做必要接口适配，与 Compose 共用同一次检查。
- 状态圆点参考 SyncClipboard 的源码实现，配合完整文字，适配明暗主题。浅色注意色适当加深，避免在浅背景上难以分辨。圆点仅作辅助，不承载独立无障碍语义。
- 主区显示词库可读取性、Rime 状态、自动同步开关和上次成功同步统计，文件大小、保存副本及历史异常文件收进详情。
- 不再显示「滚动副本」「恢复旁路」「落盘」等术语，不把历史异常文件直接描述为当前词库损坏。
- 自动同步开启后的正常摘要显示上次成功时间，日期与时间格式沿用系统设置。正在处理或失败时优先展示当前状态。
- 手动、自动共用一个结果记录来源，预览、配置操作和未执行的自动任务不会清除上次失败。任务开始通知携带忙碌状态，避免界面查询排在长任务后面而看不到进行中状态。

## 集中回归结果

首轮隔离包已通过真实界面和 SAF 的完整流程：

- 首次确认规则后，2 条支持记录进入 Google，2 条拒绝记录保留在 Rime，同步结束后为 4 条基线、空闲状态及零待同步变更。
- 再次点击「立即同步」直接完成，无预览或逐批确认对话框。
- 开启自动同步，复制后选择新目录，身份、盐、代次、基线、Native 记录及开关保持不变。
- 先选择空目录时，预览报告缺少旧快照，原记录和基线保留。复制原内容后不必重选目录，预览恢复正常。
- 实际 JobService 处理新的支持与拒绝记录，最终为 3 条 Native 记录、6 条基线，自动同步保持开启，重新读取后的预览五项变更均为零。
- 设置页显示上次同步时间及「双方共有 3 条，仅保留在 Rime 的有 3 条」。此次只核对界面文本，颜色的主观视觉验收留给用户。

证据在 `work/rime-rc2/e2e/` 的阶段 JSON 与 `status-ui.json`。该轮结束时审计包、探针及本轮公共目录已清理，正式进程和默认输入法未变化。

最新代码已通过原始 APK 重建、Rime 主机回归、选定的 Kotlin 状态测试和静态门禁。Kotlin 测试使用项目实际提供的 `testDebugUnitTest` JVM 任务，没有生成或安装正式包名的 Debug APK。

### 最终远程设备回归

设备恢复连接并由用户解锁后，最新隔离包完成同一端到端流程及以下剩余检查：

- 先选择空目录时，手动同步记录缺少快照的错误，Native 保持 2 条、基线保持 4 条。实际后台任务也保留原记录和自动开关，不把缺失文件解释成删除。
- 补齐文件后，只读预览恢复正常但不清除上次失败记录。实际自动同步成功后才清除错误，Native 增至 3 条、基线增至 6 条，五项待同步变更为零。
- 在 Rime 端删除一条已同步记录后，实际 JobService 将 Native 从 3 条减至 2 条，自动同步保持开启，任务完成后无待同步变更。
- 为复现「后台任务进行中状态不能等任务结束才刷新」的情形，探针只在隔离包中暂时持有现有保存锁 30 秒。实际后台任务等待期间，界面显示「正在同步词典……」，释放锁后正常完成。此项未终止保存，也未对正式词库做故障注入。
- 在已选目录的本设备合成快照中换入另一身份后，运行时报告身份冲突并关闭自动任务，Native、原身份和代次不变。还原快照后，通过唯一的「立即同步」入口恢复成功，错误清除、代次增加，自动开关仍保持关闭，由用户决定是否重新开启。

最新证据为 `work/rime-rc2/e2e/remote-run.log`、阶段 JSON、`busy-ui.json` 和 `cleanup.json`。隔离包、探针、本轮公共目录及 UI dump 均已清理，正式进程和默认输入法在隔离回归期间未变化。

这些是强制触发实际 JobService 的回归，不等于已等待自然调度或完整退避时长。任意中断窗口、任意事务阶段换目录、16 KiB Native 运行时以及完整视觉／TalkBack 体验仍不在本轮结论内。
