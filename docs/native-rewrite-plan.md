# Google 拼音原生重写研究计划

## 目标

本计划服务于 Comeback Google Pinyin Input 的长期原生重写。最终目标是以 Kotlin 为主要开发语言，从零建立可独立构建、调试、测试和演进的 Android 输入法，并尽可能覆盖当前兼容版的全部有效功能。

目标产品的行为基准按以下优先级确定：

1. 当前维护者修改后的 Comeback Google Pinyin Input
2. 固定版本 Google 拼音输入法 `4.5.2.193126728`
3. Gboard 拼音中可以补足前两者缺口的行为
4. 经过明确记录的新产品决策

Gboard 只作为补充资料，不改变项目以 Google 拼音及其兼容版为主体的方向。

本阶段只开展研究，不开始原生版本的功能实现。正式开发至少等待 Rime 用户词典双向同步完成、合并并形成稳定数据契约后再启动。

TalkBack 专项适配和触摸探索暂不纳入本计划，也不作为研究阶段、开发阶段或最终替换的验收条件。后续是否支持，由独立规划重新评估。

## 最终结果的定义

「尽可能实现软件的所有功能」不是要求逐字节复制原 APK，而是要求对冻结基准中的每项能力作出可追踪的处理决定：

- 原生重写并保持行为
- 在保留用户价值的前提下重新设计
- 使用来源和许可证明确的替代实现
- 因服务失效、平台淘汰或无法合法分发而明确退役
- 暂时无法实现，但记录缺失能力、原因和后续条件

任何能力都不能因为难以逆向或实现而从计划中静默消失。最终是否达到替换条件，以完整能力清单、行为验收、数据迁移、性能和长期稳定性共同判断。

## 基本原则

### 研究手段不限于黑盒观察

允许并预期使用以下手段理解原版和兼容版：

- APK、DEX、Smali、资源和 Manifest 静态分析
- Java 与 native 调用边界分析
- native 库导入导出、字符串、数据段和调用关系分析
- 动态调试、受控日志、方法跟踪和性能跟踪
- 文件格式、Preference、数据库和词典状态差分
- 真机上的输入行为对照实验
- Android 公开 API、论文和开源输入法的交叉研究
- Gboard 的静态分析和可观察行为对照

逆向结果用于理解逻辑、识别状态和建立实现参考。未来原生工程不机械继承混淆类结构、Smali 控制流、历史兼容层或无法说明用途的常量。

### 区分事实、推断和决策

每项研究必须明确区分：

- **已确认事实：** 可由固定输入、可重复实验或源码直接证明
- **推断：** 能解释现象，但证据尚不完整
- **未知：** 当前没有足够证据
- **实现决策：** 新版本准备采用的设计，不冒充原版事实

推断转为事实时，应补充能够复现的证据。新证据推翻旧结论时，直接修正文档并保留 Git 历史，不同时保留两套互相冲突的现行结论。

### 记录来源和适用版本

每项能力或行为使用以下来源标签：

| 标签 | 含义 |
| --- | --- |
| `ORIGINAL` | Google 拼音 4.5.2 原始能力 |
| `COMEBACK` | 当前兼容版新增、修复或重新设计的能力 |
| `GBOARD` | 从固定版本 Gboard 获得的补充参考 |
| `ANDROID` | Android Framework 或公开平台契约 |
| `NEW` | 原生重写时作出的独立产品决策 |

涉及运行时观察时，同时记录应用版本、提交、Android 版本、设备、输入设置和用户数据前提。

### 原始材料与结论分离

计划纳入 Git 的内容以可审阅的研究结论、必要证据、复现步骤和自行编写的工具为主。完整反编译目录、批量资源导出、设备私有数据、临时日志和大型二进制分析产物保留在本地，不作为仓库长期源码。

不得收集或提交真实用户输入、候选正文、联系人正文、剪贴板正文、手写轨迹、私有用户词典或其他敏感内容。行为语料使用人工构造或来源明确的公开数据。

未来发布原生版本前，应单独审计代码、资源、词典、模型和依赖的来源与许可证。把反编译逻辑改写成 Kotlin 不会自动改变原始材料的权利状态。

### 功能清单

`feature-inventory.md` 是范围的唯一总表。每项功能至少包含：

- 功能名称和来源标签
- 所属基准版本或提交
- 用户入口和触发条件
- 输入、可见结果和持久状态
- Java、native、资源或 Android Framework 依赖
- 当前证据和研究状态
- 原生版本处理决定
- 验收方法
- 已知缺口

详细文档解释机制，功能清单只链接详细文档，不在多个位置重复维护同一状态。

### 架构图

`architecture-map.md` 记录原版的职责和数据流，不以混淆类名作为未来模块边界。至少覆盖：

```text
Android InputMethodService 生命周期
→ 输入会话与 EditorInfo
→ 键盘模式和布局
→ 按键、手势或手写事件
→ composing 状态
→ Java/native 解码边界
→ 候选生成与分页
→ 候选选择和提交
→ 用户学习与词典持久化
```

混淆类名、JNI symbol 和资源 ID 可以作为证据附录，但正文使用稳定职责描述。

### 行为样本

行为样本采用结构化格式，至少表达：

- 基准身份
- 初始设置和输入字段类型
- 用户动作序列
- composing 文本变化
- 候选前若干项及选中状态
- 提交结果
- 持久状态变化
- 是否依赖历史学习数据

样本期望值来自固定基准的实际观察，不使用未来被测实现的算法计算。

## 完整能力地图

第一轮盘点必须覆盖以下领域。此列表是调查入口，不替代最终功能清单。

### 1. 应用与 IME 生命周期

- 安装、启用、选择和首次引导
- `InputMethodService` 创建、启动输入、显示、隐藏和销毁
- `EditorInfo`、input type、IME options 和 private options
- 输入应用切换、字段切换、屏幕旋转和进程重建
- 全屏、横屏、分屏、浮动和大屏行为
- 语言、键盘和其他输入法切换
- 语音输入往返
- 锁屏、解锁和系统窗口生命周期

### 2. 拼音输入引擎

- 拼音字符规范化
- 全拼音节识别和歧义切分
- 撇号分隔、简拼和不完整拼音
- 模糊拼音
- 双拼方案及零声母规则
- 拼音图、候选路径和长句解码
- 单字、词组和整句候选生成
- 候选排序、去重、分页和增量请求
- 部分候选选择、重新组词和剩余拼音处理
- 数字、日期、网址及中英文混合输入
- 错拼、容错和无法解码时的回退

研究不能预设原版一定使用某一种公开 HMM、N-gram 或搜索算法。具体模型以 Java/native 边界、数据文件和实验结果为证据。

### 3. 词典、语言模型与用户学习

- 中文基础词典及索引
- 英文词典和建议
- 联系人建议
- 自定义短语
- 用户词典文件及备份文件
- 中英文学习触发条件
- 词频、时间、衰减、删除和清空语义
- 候选选择对后续排序的影响
- 导入、导出、合并和损坏恢复
- SAF 自动备份和版本轮换
- Rime 双向同步的数据模型、冲突和删除语义
- 可替代基础词典、语料和模型的来源及许可证

词频值不默认可以在 Google 拼音、Rime 和未来引擎之间直接换算。先确认各自语义，再决定迁移规则。

### 4. 键盘和输入模式

- 中文全键盘
- 中文九键及消歧
- 双拼
- 中文笔画
- 英文大小写和建议
- 中文、英文滑行输入
- 中文手写、笔迹渲染和识别
- 数字、电话、日期时间和密码键盘
- 符号、Emoji 和分页
- 实体键盘
- 单手模式和键盘高度

每种模式分别记录布局、事件协议、候选来源、提交规则、学习行为和模式切换时的状态保留。

### 5. 候选、Header 与输入交互

- 固定和展开候选
- 候选分页、滚动、触摸取消和物理键选择
- 原生 Candidate 的展示、选择、删除和无障碍语义
- 统一 Header 平台和功能仲裁
- 简繁快速切换
- 剪贴板候选及敏感内容处理
- Inline Autofill 远端 Surface 托管
- Header 操作按钮和空间优先级
- 按键音、振动、弹出反馈和设置预览

当前兼容版已经形成的 Clipboard、Inline Autofill 和 native action 数据边界应作为目标行为，不要求未来实现沿用现有补丁结构。

### 6. 视觉、主题与可访问性

- 内置浅色、深色和彩色主题
- 自定义图片主题及裁剪
- 动态配色和系统自动主题
- 键盘、候选、Header、手写和底部视觉面的坐标关系
- 三按钮和手势导航
- covering-IME 与 WindowInsets
- 高刷新率和动画
- 字体缩放、显示缩放、横屏、分屏和 RTL
- 基础可访问性属性和系统语义

视觉研究优先提取布局规则、状态和设计 token，不默认复用原版受保护资源。

### 7. 设置和数据管理

- 原始 Preference key、类型、缺省值和依赖
- API 35+ Compose Material 3 设置
- API 17–34 旧设置行为
- 首次引导状态
- 主题、输入、键盘、反馈和手写设置
- 词典健康状态
- 备份、立即备份、导入和恢复
- 联系人权限和词典清除确认
- 启动器图标控制
- 关于、许可证、隐私和外部链接
- 设置升级和旧数据迁移

### 8. 平台、性能和安全

- 支持的 Android 版本和 ABI
- target SDK 演进
- 4 KiB 与 16 KiB page size
- 启动、按键到候选、分页和提交延迟
- CPU、内存、存储和电量
- 主线程 I/O 和并发保存
- native 崩溃、Java 崩溃、ANR 和状态恢复
- 密码字段、敏感剪贴板和日志边界
- 权限、组件导出、Provider 和网络访问
- 可复现构建、签名、升级和回滚

### 9. 历史及失效功能

- Google 账户词典同步
- Firebase、统计和反馈上传
- 在线词典更新
- 依赖已关闭服务器或私有认证的能力

这些能力仍进入功能清单，但可以作出「退役」或「以本地能力替代」的明确决策。

## 研究阶段

研究按依赖关系推进，不以预估日期强制结束。一个阶段未达到出口条件时，不用文档数量代替结论质量。

### 阶段 0：冻结范围和建立清单

任务：

1. 盘点原版 Manifest、组件、权限、资源、assets、DEX 和 native 库
2. 盘点全部设置项、键盘布局、输入模式和用户入口
3. 从 `CHANGELOG.md`、设计文档和补丁中提取 Comeback 新增能力
4. Rime 同步合并后更新兼容版基准
5. 建立功能清单并标记证据状态

出口条件：

- 每个用户可达入口都已进入功能清单
- 每个已知后台组件和持久数据文件都有归属
- 原版、Comeback、Gboard 补充和退役能力可以区分
- 未知项被明确记录，没有用推测填空

### 阶段 1：输入生命周期和状态机

任务：

1. 建立输入会话、键盘模式、composing 和候选状态图
2. 分析 `InputConnection` 读写及批量编辑边界
3. 调查字段切换、光标变化、删除、取消和提交
4. 对照密码、网址、邮箱、数字及普通文本字段
5. 建立代表性行为样本

出口条件：

- 可以从用户事件解释到最终提交或取消
- 状态图覆盖正常路径、模式切换和生命周期中断
- 尚由 native 黑盒决定的状态已单独标出

### 阶段 2：拼音解码与 native 边界

任务：

1. 定位 Java 到 `libhmm_gesture_hwr_zh.so` 和数据 bundle 的完整边界
2. 识别初始化、输入更新、候选请求、选择、学习和保存协议
3. 研究全拼切分、简拼、模糊音、双拼及长句路径
4. 使用构造样本比较输入增量与候选变化
5. 评估可独立实现的算法和可采用的开源参考

出口条件：

- Java/native 调用协议和主要状态所有权清晰
- 核心输入行为有可重复样本
- 已能提出至少一个有数据与许可证来源的替代引擎方案
- 无法确认的模型细节不会阻塞功能层规格

### 阶段 3：词典、学习和迁移

任务：

1. 研究基础词典、用户词典和备份文件的结构与职责
2. 通过受控合成词条观察学习、排序、删除和持久化
3. 记录原版导入、导出和合并语义
4. 吸收完成后的 Rime 双向同步契约
5. 设计 Google 拼音、Rime 和未来引擎之间的迁移模型
6. 调查可分发词典和语料

出口条件：

- 数据生命周期和故障恢复路径清晰
- 可以说明哪些数据能无损迁移、近似迁移或不能迁移
- 未来基础词典和模型不存在未解决的分发来源问题
- 用户学习的最低可行规则有可验证规格

### 阶段 4：其他输入模式

按以下顺序研究：

1. 中文九键
2. 双拼
3. 英文输入和建议
4. 笔画
5. 符号与 Emoji
6. 中文和英文滑行输入
7. 中文手写
8. 实体键盘及其他专用字段键盘

每种模式完成事件、候选、提交、学习、资源和 native 依赖分析。手写和滑行需要单独调查模型来源、推理性能和替代方案，不因界面可复刻而视为能力已解决。

出口条件：

- 每种模式均有实现路线或明确阻塞项
- 共用状态与模式专属状态已经区分
- 不以全拼结果代表其他模式已经覆盖

### 阶段 5：界面、现代功能和平台行为

任务：

1. 整理键盘、候选、Header、主题和触摸协议
2. 将现有 Compose 设置及其业务契约纳入目标
3. 整理 Clipboard、Inline Autofill、简繁切换和 Header 仲裁
4. 整理首次引导、备份、权限、导航和无障碍
5. 建立 Android 版本、窗口、Insets 和设备形态矩阵
6. 测量兼容版性能基线

出口条件：

- 所有 Comeback 新增能力都已进入目标清单
- 用户可见行为与当前 Smali 注入方式已经解耦
- 现代 Android 必需行为具有明确验收条件
- 性能结论来自统一方法下的基准数据

### 阶段 6：重写决策和开发就绪评审

任务：

1. 汇总完整能力清单和剩余未知项
2. 确定未来工程的职责边界，不预设所有模块必须纯 Kotlin
3. 比较 Kotlin/JVM、自研 native 和开源引擎方案
4. 确定词典、模型、资源和依赖来源
5. 制定从最小输入闭环到完整替换的实施顺序
6. 明确旧兼容版与原生版的数据迁移和并行发布策略
7. 编写 `readiness-report.md`

进入开发必须同时满足：

- Rime 双向同步已经完成并形成稳定契约
- 功能清单覆盖冻结基准，没有未归类的主要入口
- 全拼核心行为、输入状态和数据生命周期已有规格
- 基础词典及语言模型存在可实施、可分发的来源方案
- 第一阶段实现范围和验收标准明确
- 原生应用可以使用独立包名和数据目录与兼容版并存
- 已知阻塞项不会让第一条真实输入链路成为一次性原型

## 未来开发的阶段边界

以下只规定研究需要支持的迁移顺序，不在当前阶段实现代码。

### 开发阶段 A：最小真实输入闭环

```text
InputMethodService
→ 按键事件
→ composing
→ 拼音切分
→ 基础候选
→ 候选选择
→ commitText
```

只覆盖普通文本字段中的中文全拼，目标是验证架构和候选延迟，不冒充日常可用版本。

### 开发阶段 B：核心日用能力

加入用户学习、用户词典、长句、简拼、双拼、中英文切换、删除重组、设置和数据持久化。

### 开发阶段 C：完整输入模式

依次加入九键、英文建议、笔画、符号、Emoji、滑行、手写和专用字段键盘。每种模式独立达到行为与性能门槛。

### 开发阶段 D：Comeback 现代能力

迁移 Compose 设置、统一 Header、简繁切换、Clipboard、Inline Autofill、词典健康状态、SAF 备份和 Rime 同步。

### 开发阶段 E：兼容、迁移和替换

完成主题、无障碍、设备形态、Android 版本、性能、稳定性和用户数据迁移验证。原生版本先以独立应用并行测试，只有达到替换门槛后才改变现有项目的主要发布方向。

## 替换门槛

原生版本不能因为「主要功能已经存在」就替换兼容版。至少需要满足：

- 功能清单中的所有项目都有最终处理状态
- 日常使用所需输入模式不存在关键空缺
- 固定行为样本通过，差异均有产品决策记录
- 候选质量经过真实语料对照，不只验证少量示例词
- 按键到候选、启动、内存和持久化性能达到实测基线要求
- 用户词典、设置和备份存在可验证的迁移路径
- 密码、敏感剪贴板、日志、权限和网络边界通过审计
- 目标 Android 版本、导航方式、横竖屏、分屏和大字体完成验收
- 连续日常使用达到预先约定的稳定观察周期
- 原生版本可以从源码独立、可复现地构建和发布

具体数值不在研究开始时猜测。先用统一方法测量当前兼容版，再在开发就绪评审中冻结候选命中、延迟、内存和稳定性门槛。

## 分支与协作

研究使用独立 worktree：

```text
维护工作区：E:/dev/comeback-google-pinyin-input
研究工作区：E:/dev/pinyinreverse
研究分支：research/native-rewrite
```

约束：

- 研究分支不修改 Rime 同步实现
- 兼容版功能仍在各自独立功能分支开发和验收
- Rime 同步合并后，研究分支通过明确 merge 或 rebase 更新基线
- 两个 worktree 不切换或删除对方正在使用的分支
- 研究文档按独立主题提交，避免一个提交混入多条未完成调查
- 临时逆向产物和设备数据不因 worktree 共享 Git 对象而自动进入版本控制

如果未来原生实现与现有 APK 补丁工程的构建、许可和发布边界明显不同，应在开发就绪评审中决定采用独立仓库还是 orphan branch，不在研究阶段提前迁移历史。
