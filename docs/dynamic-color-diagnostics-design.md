# 动态配色诊断日志设计

用于定位「用户设备上动态配色不生效」的问题。用户无法提供设备，需要在设置里
临时加一个记录与导出功能，取回现场信息。

本文只做设计，不含实施。

> **状态：已暂停（2026-10-02）。** 排查中发现 2.1.4 的动态配色失效另有原因
> —— 槽位初始化的一次性标志让升级安装拿不到动态槽位的键，与设备 ROM 无关。
> 该缺陷已单独修复，诊断功能暂不实施。已完成但未合入的 Java 埋点与 Compose
> 诊断页存放在 `work/paused-dynamic-color-diagnostics/`。
> 详见 [2026-10-02 交接记录](handoff/2026-10-02.md)。

## 一、要解决的问题

2.1.4 发布后，有用户反馈动态配色键盘在他的设备上不工作。已知：

- 开关能打开（否则用户不会报告「不工作」，而是报告「没有这个选项」），
  说明设备是 API 31 以上；
- 无法取得设备，只能靠用户回传信息。

### 1.1 现有日志为什么不够

`SystemAutoThemeCompat` 已有 `debugLog`，15 个调用点，但：

- 只写 **logcat**，普通用户取不到。
- **最关键的信息完全没有记录**。

现有日志点：

| 位置 | 内容 |
| --- | --- |
| `SystemAutoThemeCompat.java:439` | `dynamic palette unchanged` |
| `:447` | `dynamic theme package rebuilt` |
| `:504` | `dynamic template missing: <name>` |
| `:510` | `dynamic style sheet rewrite failed` |

### 1.2 最可疑的静默失败

`resolveDynamicColors`（`:452-473`）的实现：

```java
int identifier = resources.getIdentifier(resource, "color", "android");
if (identifier == 0) {
    continue;                    // 资源不存在，静默跳过
}
try {
    colors.put(name, resources.getColor(identifier, theme));
} catch (RuntimeException ignored) {
    // 异常也被静默吞掉
}
```

**如果 ROM 不提供 `android.R.color.system_*` 这一族资源，整张颜色表会是空的。**
此时：

- 改写会「成功」，只是改写 0 条规则。
- 主题包能正常生成，但内容全是模板原色。
- 键盘渲染出来和没开一样。

**这条路径没有任何日志，完全不可见。** 这是首要嫌疑。

## 二、记录什么

### 2.1 环境事实

厂商、型号、Android 版本、API level、`Build.DISPLAY`、`Build.FINGERPRINT`、
应用版本与 versionCode、是否 debuggable。

### 2.2 能力与状态

- `supportsDynamicColor()` 的返回值。
- 开关 `compat_system_dynamic_color_theme` 的实际值。
- `additional_keyboard_theme` 的当前值。
- 跟随主题 `compat_system_auto_keyboard_theme` 的状态。

### 2.3 调色板解析（最关键）

逐槽位记录：资源名、`getIdentifier` 是否命中、解析出的颜色值、失败原因。

汇总一行：`resolved N/20`。

**这是当前完全缺失、且最可能直接指向病因的信息。**

### 2.4 主题包构建

- 模板是否找到。
- **实际改写了多少条规则**（现在没有记录）。
- 包大小与条目数。
- 失败原因。

### 2.5 包内回读（用于二分定位）

包生成后**读回来**，解析样式表并记录关键槽位的真实颜色值。

这条信息能把问题一刀切开：

- 包内是**动态色** → 问题在键盘侧读取或视图重建。
- 包内是**模板色** → 问题在调色板解析或改写。

### 2.6 时间线

每次触发（进程启动、配置变更、键盘弹出）都记一条，带时间戳，
便于判断「用户开了开关但从未触发重建」这类情况。

### 2.7 异常

完整堆栈，不截断。

## 三、怎么存

- 位置：应用私有目录 `files/dynamic_color_diagnostics.log`。
- 追加写，每行带时间戳与标签。
- 单文件上限 256 KB，超出后滚动（保留最近部分），避免无限增长。
- 必须跨进程重启保留，否则用户重启一次就没了。

## 四、怎么导出

给两个入口，覆盖不同用户习惯：

1. **保存到文件**：`ACTION_CREATE_DOCUMENT`，用户自选位置（含云盘）。
2. **直接分享**：`ACTION_SEND` 配 FileProvider，用户直接发给开发者。

两者都不需要额外权限。SAF 这条路径项目已有先例（词典自动备份）。

## 五、界面

- 位置：「其他」页新增一行「诊断日志」。
- 行内摘要：日志条数、文件大小、最近一条的时间。
- 点击进入子页：查看关键摘要（环境、能力、`resolved N/20`、包内回读）、
  保存、分享、清空。

子页的摘要要**用大白话把结论摆出来**，例如
「系统调色板命中 0/20，这台设备没有提供动态配色资源」，
让用户一眼能看出结果，不必自己读原始日志。

## 六、只在 debug 构建出现

复用项目现有的能力门控机制：

- `SettingsCapabilities` 增加一个 `diagnosticsVisible` 字段。
- 用 `ApplicationInfo.FLAG_DEBUGGABLE` 判定，与现有 `debugLog` 同一套判据。
- Release 构建里这一行不渲染。

这样不需要单独的构建变体，也不会让正式版用户看到诊断入口。

## 七、怎么保证「临时」

- 记录逻辑集中在一个新文件。
- 注入点尽量少，且都用同一行调用。
- 便于问题解决后整体移除。

**不删除**已写入的日志代码，只摘掉入口，与「弃用旧设置页」的处理方式一致。

## 八、风险与边界

| 项 | 说明 |
| --- | --- |
| 日志可能含隐私 | 只记设备型号、版本、颜色值，**不记用户输入、词典内容、剪贴板** |
| 用户可能不会操作 | 摘要页要给出结论，导出按钮要有明确文案 |
| 诊断版不是正式版 | 用隔离包名构建，验收后卸载，绝不覆盖正式包 |
| 滚动上限 | 256 KB 足够容纳多次触发，又不会撑爆用户存储 |

## 九、待确认

1. 导出方式是否两个都要，还是只要「保存到文件」。
2. 是否需要同时记录**键盘侧**的读取结果（需要额外注入键盘路径，工作量更大）。
3. 诊断版用哪个隔离包名。
