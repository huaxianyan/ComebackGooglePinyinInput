# 设置备份与签名迁移

## 状态与发布边界

2026-10-16，维护者确认采用两条迁移途径：支持签名轮换的系统先经过指定迁移版，再升级新签名版本。其他情况使用设置和词库备份，卸载重装后恢复。

当前为主题分支上的首轮实现。完整宿主构建、现代设置成品门禁、target 37 门禁及 6,633 项旧资源 ID 核验已通过。设置导出、修改后导入、分组恢复页、备份目录授权和 Rime 首次同步准入已通过隔离真机流程。另一审计签名重装后的设置导入、备份目录重新授权及原 Rime 测试目录的首次同步也已通过。后续同一安装内补齐了合成非空词库导入、主题包字节恢复、非默认设置及联系人拒绝路径。非空数据跨卸载、主题像素观感和联系人实际授权仍待验收。新发布密钥已由维护者在本机生成，公开证书已核对。正式 lineage 已由 CI 生成并完成下载核对，保存在 `signing/release.lineage`。独立新签名 Secrets 已由维护者上传并在生成流程中实际使用。现有 APK 发布签名及线上 Release 均未更改。隔离 B → C 迁移版 → 纯 C 版本的覆盖升级已在 API 37 实机通过。

## 设置备份

入口位于「其他 → 设置备份与恢复」。通过系统文件选择器导出或导入 ZIP 文件，文件读写和主题检查在后台执行。导入前显示替换确认。

本轮覆盖已审计的设置页选项：输入偏好、模糊音、英文选项、手势输入、声音、振动、键盘尺寸、按键边框、手写、主题模式与主题槽位、启动器图标，以及快捷短语开关。只保存已写入的普通偏好，缺失键在恢复时仍保持缺失。

备份还包含以下内容：

- 自定义主题包及其中的图片
- 自动词库备份的间隔和保留数量，保留这两个选项的缺失状态
- 联系人建议的恢复意愿
- Rime 的设备目录名、快照文件名和自动同步间隔

词库正文沿用现有独立备份和导入入口。设置备份不是完整应用数据备份，不包含 Rime 同步数据库、身份、基线、首次成功记录、删除规则同意记录、后台任务、历史状态、目录授权、系统权限或首次引导状态。原生键盘中未进入设置页的状态是否需要迁移，仍待覆盖盘点。

备份包含用户主题图片，应保存在可信位置。导入仅接受已登记的键、类型、枚举和主题路径。解压后的设置与主题总量上限为 64 MiB，主题包作为完整文件恢复，不展开其中的路径。格式以 `SettingsTransferArchive` 为唯一实现，版本为 1。固定格式夹具独立编码，检查导出与读取。

## 完成恢复

导入成功后进入「完成恢复」，以后可从设置备份页再次进入。首次引导已经负责启用和选择输入法，此页不重复这些步骤。

按功能分组：

1. 联系人建议：仅在需要恢复时显示，直接调用现有授权入口。系统不再弹出授权框时，前往应用权限设置。
2. 自动词库备份：目录、自动开关和现有词库导入入口放在一起。
3. Rime 同步：目录、设备目录名、快照文件名、手动同步、自动开关和间隔放在一起。复用现有设置行、业务回调和确认弹窗，仅调整该页面的排列顺序。

自动备份与 Rime 自动同步在导入时关闭，由用户在恢复页明确开启。Rime 沿用正常准入条件，首次成功同步记录不从设置备份导入。未满足条件时，可以在同一组完成手动同步后开启自动同步。

跨词库配置和普通设置的恢复不是数据库级原子事务。发生错误时可能已有部分配置改变，界面需明确提示检查并重新导入。主题文件在写入偏好失败时尝试恢复原文件，不能据此宣称整个迁移具有原子性。

## 生成新发布签名

在 PowerShell 7 中运行 `scripts/create-release-signing.ps1 -OutputDirectory <签名目录>`。脚本默认生成 PKCS#12、RSA 3072 位、约 30 年有效期的发布密钥，证书名称为 `ComebackGooglePinyinInput Release`。

口令仅由 `keytool` 在本机终端交互读取。脚本没有口令参数，不保存口令。已有私钥文件会保留，重复执行仅继续导出、核对公开证书。公开信息保存为 `SIGNING-INFO.txt`，不记录口令。导出失败后保留已生成的私钥，可以核对口令后重新运行。

旧材料与新材料分目录存放，生成脚本不迁移或删除旧文件。只生成新密钥不等于完成轮换，仍需准备传承记录及 CI 身份核验。具体存储位置不写入公开文档。

维护者于 2026-10-17 生成的后继证书已通过公开证书核对：RSA 3072 位、SHA256withRSA，有效期至 2056-10-17。证书 SHA-256 为：

```text
7E258BB029FF14AE24771D21CBA9D5B0C9B0FD303D3787C6705E121122B2ACE0
```

脚本初次执行在打印证书信息时遇到 PowerShell 参数拆分错误。已为带点的 `-J-Duser.language` 和 `-J-Duser.country` 参数加引号，并通过真实公开证书读取验证，补齐公开签名信息文件。修复过程未重新生成或打开私钥。

## 生成正式签名传承记录

本机持有旧、新口令时，可以在 PowerShell 7 中运行 `scripts/create-signing-lineage.ps1 -SigningDirectory <签名目录>`。旧 keystore 和公开证书位于 `Backup` 子目录，新材料位于根目录。签名脚本共用 `signing/signing-materials.json` 中的文件名和默认别名，不复制命名规则。

维护者不持有旧 session 自动生成的口令，旧备份说明中也未找到口令字段。本次改为直接复用 GitHub Actions 中既有的旧签名 Secrets，详见下一节。前提是这些 Secrets 仍然存在且与旧证书匹配，不需要取回口令明文。

脚本使用现有 JDK 和项目固定的 apksigner，工具版本读取自完整宿主构建脚本。旧库只有一个私钥时由 apksigner 自动选择，含多个私钥时通过 `-OldKeyAlias` 指定。口令可由签名工具在终端直接询问，也可指定口令环境变量名。参数只接收变量名，不接收口令明文。

生成后自动核对公开证书链恰好包含旧、新两个证书，顺序正确，旧证书的 `installed-data` 为 true、`rollback` 为 false，与隔离验收采用的能力设置一致。只有核对成功后才保存正式文件，已有记录仅核对，不覆盖。

输出为签名目录中的 `ComebackGooglePinyinInput-release-signing-lineage.bin` 和 `SIGNING-LINEAGE-INFO.txt`。二者是公开证书及证明信息，不含私钥或口令。可以在核对后将 lineage 纳入构建输入，但本步骤不自动更改 CI、签名现有 APK 或发布。

已用真实审计 B/C 公开证书和 lineage 验证脚本的纯公开核对路径及默认工具定位，测试没有提供私钥文件。后续又用本轮新生成的合成密钥执行实际 CI 生成步骤，环境变量取口令、生成 lineage、证书绑定和私钥目录清理均通过。本地测试不代表正式结果，实际 CI 证据见下一节。

## 通过 CI 生成 lineage

维护者已同意使用独立的新签名 Secrets。新名称定义于 `signing/signing-materials.json` 的 `newSecrets`，统一使用 `ANDROID_ROTATED_SIGNING_` 前缀。旧发布 Secrets 保持原样，正常构建仍使用原签名。

本机需要 GitHub CLI，由维护者安装并完成浏览器登录。项目脚本不安装工具。PowerShell 7.2 及以上可执行：

```powershell
gh auth login --hostname github.com --git-protocol ssh --skip-ssh-key --web
pwsh -NoProfile -File .\scripts\upload-new-signing-secrets.ps1 -SigningDirectory '<签名目录>'
```

上传脚本仅询问新口令。先用 keytool 校验 keystore、口令、别名及仓库中已核对的公开证书，再通过 gh 的标准输入精确传递三项新 Secrets。私钥库的 Base64 和口令仅在进程内存中使用，不写入命令参数、文件或剪贴板。这里沿用生成脚本的 PKCS#12 单一口令设置，私钥口令与库口令相同。

上传成功后，手动运行既有工作流的新增模式：

```powershell
gh workflow run build-release.yml --ref feat/settings-transfer-signing-migration -f operation=create_lineage
```

复用已在默认分支注册的工作流路径，因此无需先合并主题分支。选择 `create_lineage` 时，整个 APK 构建和发布 job 被跳过，只生成 lineage。生成 job 仅有仓库内容读取权限，分别读取旧、新 Secrets，使用仓库中的两张公开证书固定预期身份。

产物只有公开的 lineage 和 `SIGNING-LINEAGE-INFO.txt`，Actions 保留 7 天。私钥临时目录在生成步骤的 `finally` 中清理，完成清理后才上传公开产物。正式运行成功后需下载、核对并长期保存 lineage，再接入迁移版构建。

维护者已上传三项新 Secrets。正式运行 [39046269262](https://github.com/huaxianyan/ComebackGooglePinyinInput/actions/runs/39046269262) 成功，源提交为 `1deb1cc`。生成 job 成功，APK 构建和发布 job 被跳过。下载产物后再次用 apksigner 解析实际文件，确认旧、新证书指纹及顺序正确，旧证书数据继承能力开启、rollback 能力关闭。

正式公开记录保存为 `signing/release.lineage`，SHA-256 为：

```text
c574c2546a6eeed8b158e87751240475eef74e5ea4b35a33d13169cf27bcb624
```

本次未签署 APK、安装或发布。旧签名 Secrets 仍需保留，生成 lineage 不等于可以删除旧凭据。

## 迁移版 APK 构建

手动选择 `operation=build_migration` 使用正式 lineage 和两套 Secrets。该模式限定正式包名和非 Debug 构建，只产生 Actions 资产，发布步骤明确排除此模式。普通 `build` 及当前自动发布仍使用原签名，默认行为保持不变。

```powershell
gh workflow run build-release.yml --ref feat/settings-transfer-signing-migration -f operation=build_migration -f artifact_name=signing-migration-acceptance
```

构建前分别核对旧 keystore 与既有指纹、新 keystore 与仓库中固定的新证书。旧材料沿用原 Secrets，新材料只在迁移模式读取。库口令通过 keytool 的环境变量通道使用，不放进进程参数。两份私钥临时文件在 job 收尾清理。

`signing/signing-materials.json` 定义 lineage 路径和默认轮换起始 SDK。宿主构建器、CI 参数和签名身份门禁共用该配置。构建参数只拼装一次，普通模式的复现检查读取同一份公开参数，仅替换工作目录及输出路径。迁移验收模式只执行一次完整构建。

`scripts/verify_apk_signing_identity.py` 调用固定版本 apksigner，分段验证 SDK 23～27、28～32 和 33～target SDK 的有效身份。前两段必须为旧证书，后一段必须为新证书。apksigner 在新系统区间同时列出旧 SDK 签名记录，门禁按 SDK 交集选择有效身份，不把旧记录误当作普通多签名。

三个区间属于静态签名验证，不等于对应系统均已运行验收。新门禁已用真实审计 B/C 迁移 APK 验证，正式迁移版的完整 CI 构建及下载产物核对待执行。

## 签名迁移

迁移版采用 `apksigner` 的 SDK 定向密钥轮换，而不是普通多签名。默认从 Android 13 开始使用新密钥，旧系统继续验证旧密钥。Android 9 起轮换作为显式选项保留，未经专项验收不采用。

完整宿主构建脚本增加以下可选参数，三项必须一起提供：

- `--rotation-lineage`：由旧密钥和新密钥生成的传承记录
- `--rotation-keystore`：新 keystore
- `--rotation-key-alias`：新密钥别名

新口令通过 `MODERN_SETTINGS_ROTATED_KS_PASS` 和 `MODERN_SETTINGS_ROTATED_KEY_PASS` 等环境变量通道引用。可用 `--rotation-ks-pass-env` 和 `--rotation-key-pass-env` 指定变量名，参数只接收变量名，不接收口令明文。`--rotation-min-sdk-version` 默认为 `33`，另一可选值为 `28`。

签名阶段已提取为完整构建和隔离验证共用的 `sign_aligned_apk`，仅保留一份签名参数拼装逻辑。隔离测试直接调用该函数生成 API 33 起轮换的 B → C 迁移版和不带 lineage 的纯 C 版本，两者均通过签名与对齐验证，应用载荷与原 APK 一致。

在 API 37 实机上，两次仅使用覆盖安装，均保留应用 UID、首次安装时间、四条合成词及权重、非默认单手模式、备份和 Rime 目录授权、Rime 首次成功同步资格、已启用输入法及当前输入法选择。升级后通过真实设置入口读写词库、进入编辑框初始化键盘，未要求重新引导。未卸载、清数据或重新授权。这里只覆盖当前实机，不扩展为 Android 13～16 或旧系统已实测。

正式 lineage 生成及下载产物身份核验已完成。迁移版 APK 构建接入及 SDK 定向身份门禁已实现，正式产物验收待执行。线上发布流水线尚未切换。

后续版本若只用新密钥签名且不带旧到新的轮换证明，旧版用户需要先安装迁移版。只有在迁移版实际采用了新密钥的系统上，后续覆盖升级才能成立。默认策略下，Android 12L 及以下用户需要备份后重装。迁移版 Release 和安装包需长期保留。
