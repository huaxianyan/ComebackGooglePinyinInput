# Header 快捷入口展开与收起动画研究

## 目标与当前阶段

研究左侧快捷入口展开／收起不够流畅的问题，不修改输入、候选、学习、布局、触摸或动画时长，不发布 Release。

研究分支为 `research/header-shortcut-animation`，从包含引导及可复现构建修复的主线 `37ea5ff` 创建。静态定位之后，用户授权清理旧测试包并开始实验，已完成第一轮独立审计包对照。实验代码仅在 `work/`，未改变正式补丁源，没有发布版本或覆盖正式包。第二轮已准备，但设备断开后尚未安装。

## 已确认事实

### 这不是之前已修复的候选面板动画

已发布的 API 36 高刷适配只覆盖两类运动：

- 候选展开／收起：`asq` 的两个原生 80 ms 动画，监听器为 `ass`、`ast`
- Emoji、颜文字和符号分页：拖动及 Scroller settle，精确限于对应原生 pager

两者共用 `ViewFrameRateCompat.requestHigh(View, boolean)`，只请求系统公开的 `HIGH` 类别，结束后恢复 `NO_PREFERENCE`，没有固定具体 Hz。

左侧快捷入口属于另一条原生链：`AccessPointsManager`、`AccessPointsViewHelper`、`ahb` 以及 `AccessPointsBar`。当前补丁没有将这条动画链接入上述高刷桥。不能因为候选或分页已支持高刷，就认为 Header 菜单也被覆盖。

### 标准展开路径是两阶段顺序动画

`AccessPointsManager.a(boolean)` 的标准展开分支创建外层 `AnimatorSet`，依次播放：

| 阶段 | 原生资源 | 标称时长 | 行为 |
| --- | --- | --- | --- |
| 第一阶段 | `access_points_menu_showing` | 100 ms | 菜单图标从 −180° 旋转到 0° |
| 第二阶段 | `access_points_fly_in` | 200 ms | 快捷项横向进入 |

代码使用 `AnimatorSet.Builder.before()`，不是同时播放。标准路径标称总时长为 300 ms，未计系统动画倍率及帧调度延迟。

进入阶段的 `ahe.onAnimationUpdate()` 使用原生 `AccessPointsBar` 几何计算并更新各快捷项的 `translationX`。当前读取的运动更新路径没有每帧调用 `requestLayout()`，但这不等于已经排除所有布局、绘制或线程开销。

旋转监听器 `ahf` 与进入监听器 `ahc` 还负责原有可见性切换。展开会隐藏语言／简繁槽，不能绕过这些回调或将运动改造成另一套近似动画。

### 收起另有自己的运动路径

`AccessPointsViewHelper.a(boolean)` 负责收起。原生分支使用以下资源，标称时长均为 200 ms：

- `access_points_tray_out`：同时缩放 `scaleX`、`scaleY`
- `access_points_item_fade_out`：通过 `ahj` 更新相关 View 的缩放

当前活动 Animator 保存在 `AccessPointsViewHelper`，`d()` 会取消正在运行的动画并清空引用。取消、结束和清理应由同一运动所有者管理，不应分别在单个快捷项上堆叠独立请求。

原生还包含缩放提示、闪烁、拖动及面板相关分支，本次只定位展开／收起，未将那些动画混为同一问题，也未假定当前设备一定命中每个分支。

## 尚待验证的判断

**优先假设是菜单运动没有显式高刷类别请求，但这还不是实际帧率或根因结论。**

此前候选动画的实测表明，同一旧 IME 在 API 36 下可以被稳定按约 60 fps 调度，即使 CPU／GPU 和 jank 指标正常。限定到实际运动生命周期的 `HIGH` 请求曾将候选活动帧间隔从约 16.67 ms 改善至约 8.34 ms，详见 [既有帧率研究](gboard-frame-rate-research.md)。这是选择实验方向的依据，不是菜单已经被测为 60 fps 的证据。

本问题还需区分：

1. 实际绘制节奏为低帧率，但没有 missed deadline
2. 主线程、RenderThread 或 GPU 真正超预算
3. 100 ms 旋转后才开始进入的原生时序造成主观停顿
4. 系统动画倍率、动态刷新节奏或当前菜单状态影响观察结果

不将这些可能性直接写成缺陷，也不先改插值或缩短动画来掩盖调度问题。

## 建议的下一阶段实验

使用独立、可删除的审计输入法和空白合成编辑器，不覆盖现有配色测试版或正式版。必要的临时诊断只记录几何、View 身份、动画生命周期和帧时序，按以下顺序执行：

1. 通过原生菜单入口完成一组展开／收起，确认本次实际运行的动画分支及边界。没有这个边界，整段 `gfxinfo` 的平均值不能代表菜单运动
2. 采集一次基线：分阶段对齐 100 ms 旋转、200 ms 进入及收起的帧间隔、FrameTimeline deadline 和应用渲染耗时，区分低频调度与真正掉帧
3. 在临时实验中仅为实际菜单运动请求 `HIGH`，使用同一场景对照。保留原时长、插值、运动和可见性回调
4. 核对结束、取消、隐藏及键盘退出后释放请求，空闲时返回系统默认类别。用户再判断视觉是否改善

如果开展高刷实验，应复用现有 API 中立桥，不增加第二份帧率常量或反射实现。请求应由整个活动动画的所有者统一管理，展开覆盖完整外层 `AnimatorSet`，而不是只覆盖 200 ms 子动画。

请求目标必须实际覆盖菜单图标和快捷项的运动。旋转阶段快捷条可能仍被隐藏，不能未经验证就把请求固定挂到不可见的 `AccessPointsBar` 上。第一轮已证明：共同父容器虽然可见，也不保证请求持续有效。因此，不把「找到共同祖先」当作高刷覆盖的验收标准。后续应按统一 Header 的生命周期、原生 renderer 与清理契约接入，避免各模块相互释放彼此的运动请求。

过去固定 120 Hz 及全窗口 boost 曾出现发热或无可感知收益，因此此次不恢复这些已失败方案。不启用 Perfetto 的 input 数据源，不记录输入、候选、剪贴板、触摸坐标或图片。设备临时产物在测量完成后按确切路径清理。

## 第一轮真机对照

### 方法与数据边界

旧配色测试包已按用户最新授权卸载，随后安装独立的性能审计输入法和空白合成编辑器。审计包使用独立签名、非 Debug，包名不等于正式 ID。它只服务于本次 API 36 性能诊断，不代表通过全部受支持 API 的兼容验收。

基线与共同父容器 HIGH 对照共用同一 APK、同一原生动画链。观测代码绑定整个活动 Animator，基线不请求高刷，对照复用现有 `ViewFrameRateCompat`，在开始／正常结束时请求／释放 HIGH。请求目标是菜单键与快捷条的共同 `FrameLayout`，运行时确认其可见。未改变时长、插值或业务回调。

按键位置只取自已知菜单 View 的几何，没有读取键盘文本。直接向 `SoftKeyView` 分发事件未触发运动，故该尝试不计入样本。正式采样改用系统注入，经原生 START／END 记录确认每次实际展开或收起，任一边界缺失即停止，不继续盲点。

两种模式各 6 次展开、6 次收起。Choreographer 回调只记录帧时序，不采集输入、候选、剪贴板、偏好设置或图片。

### UI 调度结果

| 请求方式 | 运动 | 样本数 | 帧间隔中位数 | P95 |
| --- | --- | --- | --- | --- |
| 基线 | 展开 | 6 | 16.676 ms | 16.811 ms |
| 基线 | 收起 | 6 | 16.672 ms | 16.886 ms |
| 共同父容器 HIGH | 展开 | 6 | 16.650 ms | 16.742 ms |
| 共同父容器 HIGH | 收起 | 6 | 16.676 ms | 16.871 ms |

基线 UI 调度稳定接近 60 fps。共同父容器 HIGH 的展开出现了部分约 8.34 ms 间隔，但未持续保持，收起没有改善。因此，该请求位置不能作为已完成的高刷修复。

这些是 UI 回调间隔，不是面板实际刷新率，也不能单凭回调频率声称每个图像帧都已呈现。

### Trace 覆盖更正

第一轮同时采集 FrameTimeline 和线程／绘制 trace。由于全系统调度事件量过大，环形缓冲覆盖了前段数据，实际保留下来的目标帧只覆盖共同父容器 HIGH 阶段，**没有覆盖基线**。

此前口头「基线 FrameTimeline 没有超期掉帧」的判断作废。完整基线 UI 时序仍有效，但不能用对照 trace 替代基线的 GPU／呈现验证。

保留的 HIGH 阶段包含 112 个展开 surface frame 和 72 个收起 surface frame，记录的 jank 类型均为 `None`，没有 late finish。对应 Choreographer 切片平均 1.617 ms、最大 6.847 ms，RenderThread 的 DrawFrame 切片平均 2.636 ms、最大 6.443 ms。这没有显示该对照阶段存在明显超期瓶颈，但不是所有场景或基线的性能结论，DrawFrame 耗时也不等于独立测得的纯 GPU 耗时。

下一轮不再采集全系统 `sched_switch`／`sched_waking`，缩小数据源并按动画时间验证 trace 覆盖，不按「第几个切片」猜测模式。缓冲区覆盖前段时，序号会改变，模式必须依据本机观测日志中的实际时间边界关联。

### 下一轮与清理状态

下一轮临时实验改为对菜单键及快捷条的实际原生 View 请求 HIGH，不增加强制重绘，不修改原生运动。该递归请求只用于定位，不是拟合入的长期 renderer 接口。新观察代码已编译、组包，**尚未安装或实测**。

设备断开时，两种 ADB 入口均无目标设备。本轮新装的性能审计包及空白编辑器暂时仍在手机，最后确认的默认项为性能审计输入法。恢复连接后先恢复正式输入法、处理临时包，再继续实验。正式包未覆盖安装，助手没有主动探测、导出或修改正式配置和词典。本轮手机 trace 文件已在断开前精确删除并核对不存在，未生成 `/sdcard` 临时文件。

正常结束路径已观测，但取消、隐藏、detach 和空闲刷新率回退尚未完成运行时验收，不将临时 probe 中的清理代码当作这些场景的实测证据。

证据在本地 `work/header-motion-research/common-host/`，包含 APK、完整 UI 时序、统计和原始 trace，修正后的 trace 查询在 `work/header-motion-research/`。它们不是正式实现来源。

## 当前结论

已确认快捷入口基线 UI 调度约 60 fps，并找到现有高刷适配未覆盖的原生链。**仅将 HIGH 请求挂到共同父容器并不可靠，不能直接据此提交修复。** 下一步验证实际运动 View 的请求行为，再确定最小长期接入点。设备离线是当前阻塞，尚无最终动画修复或用户视觉验收结论。
