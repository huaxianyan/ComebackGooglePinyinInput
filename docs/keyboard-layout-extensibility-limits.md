# 键盘布局扩展方案：为什么「每家塞一个布局」不可行，以及该怎么办

> 承接 [键盘布局插件化可行性调研](./keyboard-layout-plugin-research.md)。
> 状态：**结论已定，未动代码**。

## 一、用户提出的问题

> 「这样写出来的布局最终还是要放在应用本身里，这样如果这个开发者加一个另外一个开发者加一个，那岂不是会塞很多？」

这是上一轮「配置化布局」建议的真实缺陷，必须先承认：

**上一轮的建议回避了产物归属问题。** 无论用插件、JSON 还是别的格式，只要最终要 inflate 成 `View`，产物就必须进入输入法自己的资源表。改配置格式并不能解决「多个开发者各塞一份布局」的膨胀问题——只是把膨胀的位置从代码挪到了配置目录。

## 二、为什么会这样：layout 属性是编译期资源 id

实证（`KeyboardViewDef$a.smali` 第 230–250 行）：

```java
// 解析键盘定义里的 <view layout="@layout/keyboard_prime_bottom">
for (int i = 0; i < attrSet.getAttributeCount(); i++) {
    String name = attrSet.getAttributeName(i);
    if ("layout".equals(name)) {
        int id = attrSet.getAttributeResourceValue(i, 默认值);   // ← 编译后的资源 id
        this.b = id;
    }
}
```

`getAttributeResourceValue` 返回的是 `0x7f0400c4` 这样的**编译后 id**，`@layout/xxx` 在 aapt 打包时就被替换掉了。这个 id 只在输入法自己的资源表里有意义。

所以链条是：

```text
布局 XML → aapt 编译 → 资源 id（写进输入法资源表）→ getAttributeResourceValue 取出 id → inflate
```

**布局进不了资源表，就拿不到 id；拿不到 id，整条链就断了。** 这是 `Resources` 在 AssetManager 层的边界，不是权限问题。

## 三、由此得出的两条硬结论

### 3.1 「不重新打包输入法就能加布局」——不可能

除非放弃 Android 原生布局 XML，改用自定义 DSL，由输入法手写一个解析器把它翻译成代码构建的 `View` 树（不经过 `inflate`）。这条路等于**自建一套 UI 框架**：

- 键盘布局用到大量自有 attr 与主题变量（`LabelAlpha`、`PopupBubbleUnderlineOnDecodeLayout` 等）；
- `SoftKeyView` 的可见性、长按 merge、软键模板参数替换都依赖框架既有解析链；
- 重写意味着把这些全部再实现一遍，且每升级一次输入法就要重新对齐。

成本与风险都远超收益。

### 3.2 因此「塞很多」是设计目标错了，不是实现方式错了

「支持 N 个开发者各提供一套布局」这个目标，在输入法资源表的约束下**不存在可行的实现**。继续沿这个方向走，只会在三种结局里打转：

| 结局 | 后果 |
| --- | --- |
| 各家的布局都打进输入法 | 输入法体积膨胀，且每加一份都要发新版 |
| 输入法内置一个通用渲染器 + DSL | 自建 UI 框架，长期维护成本极高 |
| 只做极少几个固定预设 | 其实就是现在这个方案，没有「开放给开发者」 |

## 四、真正该问的问题

把诉求拆开看，「让其他开发者也能定制」背后通常有三种不同的真实需要，对应完全不同的做法：

| 真实需要 | 做法 | 是否要重打包输入法 |
| --- | --- | --- |
| A. 用户想按自己习惯挑布局（如隐藏逗号、换键位） | 输入法内置**有限预设**，用户勾选 | 否，预设随版本发布 |
| B. 用户想自己调参数（权重、键宽、显隐） | **用户侧配置**，存 SharedPreferences 或导入导出文件 | 否，配置是数据不是布局 |
| C. 第三方开发者想分发自己的布局 | 需要改输入法资源表 | **是**，只能作为 PR 合入主干 |

关键区别：**A 和 B 里，用户/开发者动的是「参数」，不是「布局文件」。** 参数可以在运行时被读进框架的既有解析链，不碰资源表，因此不产生「塞很多」的问题——因为根本没有新布局，只有不同的取值。

C 才是「塞很多」的来源，而 C 的唯一可行形态就是**往仓库提 PR**，由维护者决定是否合入。这不是技术限制，是分发模型：第三方布局想进输入法，就得走代码审查。

## 五、建议

### 5.1 当前「逗号句号开关」不要走插件方向

它就是 A 类需求，用一个开关解决。做成插件机制属于用大炮打蚊子，还会吃掉仅剩的 4 个状态位（bit 59、61–63）中的一个。

### 5.2 如果要做「可定制」，推荐的分层

```text
第 1 层（建议先做）：固定开关
  逗号显示 / 句号显示            ← 本项目当前方案，零新增机制

第 2 层（可选）：用户级参数
  把布局里可调的数值暴露成偏好项，例如
  - 空格键相对宽度
  - 底部行是否显示符号切换键
  特点：不新增布局、不新增状态位，纯参数

第 3 层（若确有必要）：用户级布局配置
  导出/导入一份 JSON（键位、权重、显隐）
  特点：需要解析器 + 校验，但仍是「数据驱动既有渲染链」
        换设备/换人只需换 JSON，不进资源表

第 4 层（不建议）：第三方布局包
  自建插件容器，成本高、约束多、状态位不够用
```

第 2、3 层的实现要点是：**扩展的是框架解析后的参数，不是框架解析的输入。** 这样才既满足定制诉求，又不会让输入法被塞爆。

## 六、如果坚持要做第 3 层，需要先确认的事

1. 配置的作用范围：全局，还是按输入语言（中文/英文）分别？
2. 配置的存储位置：`SharedPreferences` 内，还是允许外部文件（SAF）？
3. 版本兼容：输入法升级后旧的 JSON 如何降级处理？
4. 校验策略：字段非法时是回退默认值，还是拒绝加载？
5. 是否需要 UI：做成设置页里的表单，还是只支持导入导出？

这五点定下来，才谈得上「接口规范」。在此之前不建议动代码。
