# Rime 自动同步设计

> 状态：核心后台闭环已通过 Pixel 隔离回归，包括真实进程中断后的恢复、临时解析失败重试、状态刷新及冷启动零变更。重试机会使用系统命令提前触发，未覆盖自然周期时长或所有中断窗口。本功能纳入当前版本，与手动同步一起收尾验收。

用户现已授权集中实施体验期间积累的需求，不再等待上一轮体验结束。功能代码、最终工程回归及正式签名体验包安装已完成，同步功能已完成 `2.0.11-rc.2` 工程验收，后续状态区布局改进已随 `2.0.11-rc.3` 安装，当前继续日常体验，详见 [第二轮实施记录](rime-rc2-implementation.md)。

## 已确认的产品行为

- 默认关闭，由用户主动开启
- 自动执行新增、删除和复活，开启时明确告知删除行为
- 默认间隔为 24 小时，复用自动备份的单选列表，提供 6 小时、12 小时、24 小时、2 天、3 天、7 天，以小时为存储单位
- 不再使用间隔滑块，旧滑块已存储的其他合法间隔继续显示，直到用户主动选择新值
- 不要求整点执行，实际运行时间由 Android 后台调度安排，可能延后
- 每轮只处理执行时所选目录中已有的快照
- 不检查文件是否「最新」，不检测 Syncthing 或其他设备的在线状态、同步进度
- 外部文件传播、下载、缓存和版本到达时机由相应软件负责
- 保留手动同步入口，复用现有同步目录、设备身份、基线与持久化复核
- 已确认仅保留于 Rime 的记录继续生效，不在每轮重新询问

自动同步的核心目标是开启后尽量无需用户维护。允许每次重新读取整份快照，不增加用户可见的「续传模式」或要求用户理解事务阶段。普通系统中断和临时失败由程序处理，不默认变成手动待办。

自动同步不是新增的网络服务，也不是目录监听功能。开启授权不等于允许自动清空词典、重置基线、忽略故障或扩大原生拒绝例外集合。

## 已核对的现有能力

### 自动备份不能直接作为周期调度器

`DictionaryAutoBackupCompat.request(context, false)` 只检查是否到期，执行机会来自输入法既有保存检查。它没有 JobScheduler、Alarm 或 WorkManager。长期不使用输入法时不产生备份，是该功能明确的设计行为。

自动同步需要后台执行机会，不能通过复制备份代码或在每次显示、收起键盘时触发来替代。自动备份保持原有行为，本次不顺便重做其调度。

### 同步执行能力已经存在

`RimeSyncSettingsCompat` 集中持有 Rime 单线程队列和互斥状态，并统一转换错误。`RimeSyncCoordinator` 已实现预览、执行、恢复和保留拒绝项的流程，原生访问继续由 `SaveDictionaryTask.sSaveLock` 保护。

自动入口应纳入同一个队列和错误处理路径，在同一次受控操作中复用协调器的规划、执行和完整校验。不得模拟点击 Compose，也不得重新实现文件解析、同步规划、原生写入或发布事务。

手动预览的删除确认仍保留。自动任务只有在开关已开启、开启告知已经确认时，才具有自动执行删除的授权。

## 调度方案

采用 Android `JobScheduler` 的普通周期任务：

- 使用唯一任务 ID，重复设置或恢复调度时更新同一任务
- 间隔直接来自持久配置，默认值、上下界和单位换算只在业务层定义一次
- 使用持久任务保留重启后的调度，复用已有 `RECEIVE_BOOT_COMPLETED` 权限
- 不增加精确闹钟权限、网络状态约束、充电前提或常驻前台服务
- 不引入 WorkManager 或借用旧 APK 的第三方后台同步链路
- JobScheduler 从 API 21 开始可用，低版本不得加载 JobService 类；设置入口沿用现有 Rime 功能的可用范围
- 系统负责安排周期内的运行时机，不把界面间隔描述为准点保证

依据 [JobInfo.Builder 官方文档](https://developer.android.com/reference/android/app/job/JobInfo.Builder)，周期任务执行时间具有弹性，持久任务也不等于准点承诺。真实执行仍受系统后台限制影响。

任务启动后只做资格检查和异步派发，SAF 与词典 I/O 不进入主线程。普通周期与临时失败后的重试共同管理同一个任务，失败后延后执行并退避，不制造短周期恢复循环，也不为每次重试增加用户提示。具体重试时机在实现中集中定义，不增加用户必填设置。

## 开关与异常边界

### 开启

需要目录配置完整、授权可用、已有成功同步记录，且没有待处理事务。开启时展示确认说明，例如：

> 开启后，应用会按所选间隔同步 Google 拼音与此目录中的词条，包括新增、删除和重新添加的词条。执行时机由系统安排。

取消确认时保持关闭。确认后保存开关并安排任务，不能仅改变界面开关而丢失调度。

### 与手动操作交错

自动任务与手动同步共用现有互斥入口，避免同一 Rime 事务并行执行。遇到已有操作时不抢占、不弹出确认框，也不创建第二份事务。自动备份和导入保留独立业务队列，仅共享既有 Native 锁。

### 失败与中断

- 系统回收进程、任务被停止或设备重启后，下次获得运行机会时自动检查实际状态并继续同步，允许重新读取整份快照
- 已有事务尚未结束时先按现有日志和幂等恢复规则收敛，不丢弃已提交的阶段，也不要求用户例行点击恢复
- 临时目录访问失败或本轮输入快照发生变化时保留可恢复状态，延后再试，不判断外部文件是否最新，不弹出每次失败的提示
- 区分暂时无法访问与持久授权失效，确实需要用户重新授权时才提示重新选择目录
- 新的原生拒绝或持久化复核失败仍执行既有安全校验，不盲目重复写入；无法安全自行处理时再请求用户介入
- 已确认的 Rime 保留记录正常沿用，不自动清除故障记录或重建基线，也不擅自扩大未经授权的拒绝例外集合
- 系统停止任务时不等待主线程，也不强行中断 Native 持久化临界段，不把被中断的运行记为成功
- 用户关闭开关后取消周期任务和待重试任务，已经进入事务的操作按既有安全边界结束或留下恢复记录，不承诺系统一定允许其运行至完成

只处理当前文件，不等于取消事务一致性校验。既有输入快照变化检查、Native 完整复核、Bridge 身份校验及文件发布协议继续保留，但不据文件修改时间猜测它是否为外部软件的最新版本。

## 最小实现范围

1. 在 Rime 业务层增加自动开关、间隔、暂停原因和调度协调，复用现有配置与结果边界
2. 增加单一 JobService 适配层及版本受控的 Manifest 注册，不新增同步执行器
3. 在现有 Compose Rime 区域增加自动开关、开启告知、间隔设置和暂停状态
4. 接通开启、关闭、间隔修改、应用更新及失败后的调度一致性
5. 保留手动同步和恢复行为，不要求重新选择当前目录或重建已有基线

状态页词条数误用 `getDictionarySize()` 的已知缺陷仍是发布前必修项，与自动同步分别处理，不把错误的 53 万显示当成压力测试规模。

- 默认 24 小时及 6～168 小时边界，取消开启确认后仍关闭

#### 统一体验目标

用户明确要求：上述调查用于提高同一套同步流程的可靠性，而不是把内部细节拆成更多用户操作。用户选择目录后，点击一次手动同步或等待自动同步即可，程序负责可以安全判定和完成的兼容处理、目录迁移、状态延续、重试与恢复。

合法的同一同步关系迁移应作为内部处理，不新增要求用户判断设备身份、修复基线、删除文件夹或执行独立迁移／恢复步骤的流程。手动与自动入口共享这些规则，不各自维护一套容错逻辑。只有缺少必要授权、存在无法安全判断的冲突或其他确实需要用户决定的问题，才中断并说明具体原因和可执行的操作，不能让用户反复尝试来推动程序内部状态。

验收重点是正常路径一次操作完成、可恢复问题由程序处理、自动同步持续可靠运行，同时保留完整持久化复核与数据安全边界。不以隐藏错误或宣布部分失败为成功来换取表面顺畅。当前已按后续授权集中实施，进度见 [第二轮实施记录](rime-rc2-implementation.md)。

#### 首次手动同步操作过多

用户认可「首次手动同步成功后才能开启自动同步」这一前置条件，但希望手动同步与自动同步一样，正常情况下只需点击一次，读取、规划、执行、安全恢复和收尾均由程序完成，不要求用户反复推动中间步骤。

后续实现目标：保留首次成功同步的准入条件，简化手动入口的正常流程，完成后直接给出结果。必须保留完整持久化复核与数据安全边界，不能以减少点击为由静默扩大 `RIME_ONLY` 排除集合。只有确实无法安全自动处理、需要用户作出决定的情况，才要求额外操作。

用户在内容分析和隔离编码对照后，已接受以下处理方向：这些特殊编码条目不进入 Google 拼音的影响很小，不为导入它们投入复杂兼容工作。首次说明并接受规则后，手动与自动同步统一处理可安全判定为无法直接转换的记录，复用 `RIME_ONLY` 保留在 Rime，不逐批要求确认，不阻塞其余可正常同步的条目。结果提供仅保留在 Rime 的数量，查看详情不作为完成同步的前置步骤。

不自动补拼音、改编码或删除原记录，不为提高覆盖率建设新的编码转换器、跨语言写入路径或逐词修正机制。用户进一步确认，本版本不对被中文词库拒绝的英文记录进行二次处理，不尝试转写英文用户词典。Google 拼音原有的英文输入、学习、备份和导入能力保持不变。实际自动判定边界仍需在实现时明确，稳定重复拒绝本身不等于已证明编码不兼容。原因不明的原生失败、目录访问故障、保存失败和持久化复核异常仍走对应错误处理，不能用跳过条目掩盖。该策略已在第二轮代码中实现，加入空副本拒绝验证与合成对照，不只依赖重复失败。这些改动已通过隔离包回归，并包含在已覆盖安装的 `2.0.11-rc.2` 中，尚不等于已完成日常体验验收。

#### 更换目录并复制原有内容后，同步持续失败

用户报告的操作与现象：

1. 已完成同步配置并开启自动同步
2. 更改同步目录，将之前目录的内容复制到新目录
3. 自动同步被关闭，界面要求先手动同步一次
4. 手动同步持续失败，提示用户检查其他设备的词典文件
5. 用户删除新目录中的本设备文件夹后，才能完成手动同步

自动同步关闭与要求再次手动同步是报告中的完整操作背景，不将这两项本身认定为故障根因，也不预先承诺任意换目录都无条件保留自动开关。

**隔离复现已完成，修复尚未实施。** 本轮复用非 Debug 的 `4520424` 审计 APK，通过本机 ADB 和真实 Compose 页面配置专用源目录，用两条合成词条完成同步并开启自动同步。将源目录中的 peer 和本设备快照完整复制到新目录后，在设置页选择新目录，再点击手动同步。生产预览门面再次调用也返回相同的合并错误。

已确认的状态变化：

- 目录切换前，Native 和同步基线各有 2 条记录，本地设备身份与本设备快照一致，自动同步开启
- 目录切换后，本地设备身份和 hash salt 重新生成，基线从 2 条变为 0，generation 从 2 变为 0，自动同步关闭且任务被取消
- 复制前后以及失败后的文件 SHA-256 均一致，快照仍保留原设备身份，Native 仍为 2 条
- 生产预览返回 `ERROR_PREVIEW_RIME_MERGE`（14），直接内存合并的具体异常为 `Bridge snapshot user identity changed`
- 保持这些文件不变，只在临时内存合并时使用快照中的原身份，合并即可成功，没有修改私有配置或发布文件

根因位于 `RimeSyncSettingsCompat.configureState()` 与 `RimeSyncStateStore.configure()` 的组合：前者只在完全没有 Profile 时尝试从快照恢复身份，后者把根 URI 改变视为新配置，生成新的身份和盐并清空同步状态。已有配置迁移目录时因此产生「本地新身份、文件旧身份」的冲突，`RimeSyncCore.merge()` 随后按身份一致性规则拒绝本设备快照。问题不是本轮复制文件损坏，而是程序没有区分迁移原有同步数据与建立新的同步配置。

已从审计 APK 资源和生产错误映射核对对应文案为「Rime 设备词典无法合并，请检查各设备的用户词典文件后重试」。它没有指出本设备身份变化，无法给用户有效指引。本轮未从 UI 树捕获瞬时 Toast，不将资源映射核对描述为提示截图验收。

后续修复应安全识别同一同步关系的目录迁移，处理既有身份、基线、盐和排除状态的延续，不能只关闭身份校验或要求用户删文件。内存合并对照仅定位失败条件，不代表迁移修复已经完成，也没有验证所有新目录或不同步关系之间的切换。结束后隔离包、探针、两个专用目录及本轮临时探针 APK 均已清理，正式包词库没有访问，正式包进程及默认输入法保持不变。

验收目标：迁移的是合法、完整且可确认归属的原有数据时，应能在保留本设备文件夹的情况下完成同步。由程序处理可以安全完成的迁移与恢复，不能把删除本设备文件夹作为正常操作要求。若确有冲突或数据不完整，提示必须说清问题和可执行的处理方式，不能循环要求用户检查无关目录。用户已采用的删除操作仅作为现象记录，不作为推荐方案，也不授权程序自动删除本设备或其他设备的数据。

修复后围绕上述两个实际场景完成针对性回归，再进入发布流程，不以旧版已通过的验收替代新改动的验证。
