# 2026-11-04：放弃原生重写，清理研究分支

## 决定

- 采用「保留原版 `.so` 黑箱，Java／Android 层维持正常源码」的路线，不再逐函数重写原生库。
- 原生层缺陷只在 Java 侧规避，不做二进制级的修改或替换。
- 后续构建方向定为摆脱 apktool 工具链，具体方案待评估，本轮不落实现。

判断依据：把闭源二进制的反汇编逐函数抄成 C++，得到的不是可维护源码，改它的前提永远是先反汇编看一眼；同时这批代码是 Google 代码的衍生作品，放在公开仓库有授权风险。

## 仍然成立的结论

原版 APK 的五个原生库在 16 KiB 页下有真实的加载问题，这一点与分支清理无关，继续有效：

| 库 | `PT_LOAD` 对齐 | 原样结果 |
| --- | ---: | --- |
| `libhmm_gesture_hwr_zh.so` | `0x1000` | 与 16 KiB 不同余，加载失败 |
| `liben_data_bundle.so` | `0x10000` | RELRO 尾与可写数据同页 |
| `libgnustl_shared.so` | `0x10000` | 同上 |
| `libhwrword.so` | `0x10000` | 同上 |
| `libpinyin_data_bundle.so` | `0x10000` | 本来就没问题 |

当前构建靠 `scripts/rewrite_elf_16kb.py` 重排、`scripts/audit_elf_page_size.py` 审计，并在 16384 页模拟器上验过加载。缺口是只有模拟器与 4 KiB 真机证据，没有 16 KiB AArch64 真机验收。

## 追记：首启崩溃修复与无 apktool 全链路验证

### 首启崩溃（两层）

1. `apr.onFinishInflate` 无条件把 inflate context 强转成引导 Activity（`apy`）来算
   「Step N」标题；同页引导在 IME 服务环境渲染时必崩。修复：`instance-of` 守卫，
   非 Activity 环境保留布局自带标题，Activity 路径不变（`scripts/apply_patches.py`）。
2. 守卫生效后暴露下一层：IME 侧引导 def 直接 inflate `first_run_single_page.xml`，
   容器强转 `SoftKeyboardView` 失败（页面根是 LinearLayout 系）。该页设计上属于
   引导 Activity；IME 侧首启的正确形态是 Dashboard 四布局选择器
   （见 `docs/first-run-dashboard-state-research.md`）。清数据重走首启后
   引导 Activity → 完成 → Dashboard → 打字全部正常，第二层不再复现；
   def 选择链的引用点未完全定位，是遗留线头。

### 无 apktool 链路（已跑通并上设备）

`work/no-apktool-spike/full-chain.sh`：解码 → 打补丁（含首启守卫）→ 4 库 16 KiB 重写 →
gradle 宿主（跳过 apktool）→ 独立 smali 汇编旧 dex（`build_no_apktool.py --dex-only`）→
`assemble_compose_host_apk` 合并 → 换入重写库 → `zipalign -P 16` → `apksigner`。

- 门禁：16 KiB 审计 6 库 `failures=0`、签名校验通过、dex 3526 类 27422 方法。
- 真机（4 KiB 页，Android 17）：键盘呼出、打字、Compose 设置页正常，无崩溃。
- 链路上修的三个坑：重复合并（`host.apk` 本身已是合并产物）；宿主 prep 删掉
  manifest `package` 后 aapt2 link 需要 `--manifest-package` 补写；
  「从原包复制未重建条目」会静默覆盖重写过的原生库（换库脚本已带匹配数断言）。

### 边界

- 本轮验证是构建等价 + 冒烟，不是完整功能验收；候选、学习权重、手写、主题等
  原生行为是否与正式包一致，发布前需按常规验收范围过一遍。
- spike 签名是临时密钥库，只服务验证包；正式发布仍走既有签名通道。
