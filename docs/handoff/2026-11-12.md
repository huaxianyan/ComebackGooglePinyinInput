## 9.6 万条丢词：补到的机制证据

11 日那份记录写了现象、判定依据和恢复步骤，但没有解释「文件 21.64 MB、引擎只读到约 3,552 条」
是怎么出现的。12 日补了一个实验：

把 10,000 条、1,610,688 字节的词库截断到 966,412 字节后重新注册，`getDictionarySize()` 与
`getDictionaryCount()` 仍报 50000 / 49996（来自文件头部），枚举 `getAllEntries()` 时
`SIGBUS` 崩溃，且没有生成 `_bak`、`_tmp` 或 `_unreadable`。

结论：

- 词库是 mmap 的，文件比头部声明短时原生不是报错而是崩溃。所以那次事故**不是文件损坏**。
- 它是「头部与索引只指向一小部分记录、文件本身完整」的逻辑塌陷，和「补回 96,670 条只增长
  226,600 字节」的现象自洽。
- 这种塌陷只能靠整文件恢复，无法在原文件上重建索引；恢复后必须重启输入法，因为旧文件已被 mmap
  占用。这也是兜底提示「重启后生效」的真正原因，不只是让显示更新。

触发时刻仍只能缩到 11-07 20:19 至 11-09 01:40 之间，那段时间没有日志。实验过程见研究分支
`research/dict-import-weights`。

## 恢复只能整文件替换，且必须重启输入法（已验证）

同一组实验还回答了两个实现问题：

| 操作 | 结果 |
| --- | --- |
| 换掉文件后继续用原句柄 | 仍读到旧内容（视图来自 mmap） |
| 调 `refreshMutableDictionaryData(USER_DICTIONARY)` | 没有变化，不重新绑定已有句柄 |
| 关掉再注册一个新 accessor | 读到新文件的内容 |

所以刷新救不回塌陷视图，「重启输入法后生效」是唯一可靠路径，不是保守说法。另外字节恢复必须用
rename 覆盖：在原文件上写会截断正在被 mmap 的文件，下一次读取直接 SIGBUS。`DictionaryFileSnapshot.restore()`
已改成写临时文件再 rename，恢复完成后本次检查直接返回，不再用陈旧计数覆盖恢复提示。

## 埋点：保存边界的尺寸日志

为了让下次塌陷能定位到具体时刻，守卫在每次保存边界记一条尺寸样本：

```
save_journal = 1794419756782:0/-1;1794419808395:14144/2784;1794419914997:2784/2784;...
```

只存时间、主文件大小和 `_bak` 大小，最多 12 条，不含任何词条内容。塌陷时把
`file-collapsed 2784/14144` 或 `count-collapsed 40/2` 连同样本写进 `last_debug`，并保证收尾的
`worker-finished` 不会覆盖它。真机复验：塌陷后 `last_debug` 里能看到文件从 14144 掉到 2784 的
那条样本，文件随后恢复为 14144。

下次再出现同类事故，这份日志能直接指出是哪一次保存把词库写小的，而不用再靠备份文件大小反推。

用户侧也能看到：状态页展开详情里多了一行「最近几次保存时的大小」，真机塌陷复现后显示为
「14 KB、14 KB、3 KB、3 KB、14 KB」，下跌一目了然。若上一次动作是文件恢复，状态行改为黄点
「词库文件已自动恢复，重启输入法后生效」，而不是用引擎的旧视图报「减少到 0 条」吓人。
此时详情里的「中文词条：0 条（此前最高 40 条）」是真实情况：引擎还持有恢复前的文件，重启后才更新。
