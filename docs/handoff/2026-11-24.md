# 2026-11-24 悬浮键盘拖动手柄改到卡片底部（方案 F）

## 本轮结论

悬浮键盘的手柄从「卡片上方一条横条」改成「卡片底部内侧的灰色胶囊条」，也就是原型里的方案 F。
视觉、拖动、位置记忆都在真机上验证过，测试包是 `...floatingtest`。

## 两个坐标 bug（这次的真正原因）

第一次改成卡片底部后，胶囊画在了 `z x c v b n m` 那一行上，而且拖不动。原因有两个，都在坐标系上。

### 1. `getGlobalVisibleRect` 在 IME 窗口里返回的是 content 坐标

IME 窗口原点在屏幕 `(0, 172)`，content 又在窗口内 `(0, 0)`。
`getGlobalVisibleRect` 返回的矩形已经少了一次窗口原点，再减一次 `getLocationOnScreen` 的偏移就多减了 172 px，胶囊因此被抬高一整行。

修法：手柄定位统一用「屏幕坐标相减」。

```java
int[] areaLocation = new int[2];
area.getLocationOnScreen(areaLocation);
int[] hostLocation = new int[2];
host.getLocationOnScreen(hostLocation);
int left = areaLocation[0] - hostLocation[0];
int top = areaLocation[1] - hostLocation[1] + cardHeight - handleHeight;
```

`getWidth()` 是缩放前的值，水平/垂直尺寸要自己乘 `appliedScale`。

### 2. 触摸区 `touchableRegion` 少了一块，手柄收不到事件

同一个原因：`region` 用 content 坐标写进窗口的 touchable region，卡片底部那条被排除在外，
手指按在胶囊上事件直接被窗口丢弃，`onHandleTouch` 一次都没进。

**第一次修错了，代价很大**：把 `visualRegion` 改成「屏幕坐标减 decor 位置」，
但阶段 2（`6e3a253`）在 `applyInsets` 外层已经做过一次同样的 `region.offset(-decorLocation)`。
两处叠加就是减两次，整个 region 偏上 172 px，卡片下半部分（所有按键加胶囊）全部落到区外，
**按键彻底没反应**。`dumpsys input` 里看到的值是对的，因为那一次调用时窗口还没定位、
`decorLocation` 恰好是 `0,0`，窗口定位之后才双重减。

正确的分工：`visualRegion` 只报屏幕坐标，转成窗口坐标由外层的 `offset` 统一做一次。

```java
// visualRegion：不做任何减法
out.set(areaLocation[0], areaLocation[1],
        areaLocation[0] + width, areaLocation[1] + height);

// applyInsets：唯一一次转换
region.offset(-decorLocation[0], -decorLocation[1]);
```

不要用「把 region 拉长到窗口底」来绕过：那样键盘浮到屏幕中部时，下方到屏幕底都会挡住应用触摸。

### 排查时踩的两个坑

- **拼音输入法点字母键不会直接插入字符**，先进入编码、等选词。看到输入框没字就断定「键盘坏了」是误判，
  应该看候选栏，或者点 `?123` 看布局会不会切换。
- **`adb shell input tap` 的按下时间几乎为零**，测不出按键反馈。用
  `adb shell input swipe x y x y 120` 按住 120 ms 再松开。

### 3. 胶囊要在灰带里居中，不是在触摸条里居中

灰带跟着键盘一起缩放（34 dp → 65 px），手柄本身不缩放（20 dp → 52 px）。
在手柄里居中会让胶囊骑到灰带顶边上，所以加了 `setBarCenterFromBottom()`，由 compat 每帧传入 `area.getPaddingBottom() * factor / 2f`。

## 闲置淡化

不操作 5 秒后整张卡片（含灰带和胶囊）淡到 50%，碰一下立刻恢复。

实现要点：探针视图。按键会消费自己的触摸，挂在键盘容器上的 listener 永远不会触发，
所以往窗口里加了一个透明的全屏 View（`idleProbe`），它的 `OnTouchListener` 返回 `false`，
事件继续往下发给真正被点中的按键。`DOWN` 唤醒并重置计时，`UP`/`CANCEL` 重新开始计时，
拖动期间不淡出。

`setAlpha` 不影响命中判定，淡到 50% 时按键照常可用。

过渡用 `view.animate().alpha()`：淡出 `IDLE_FADE_OUT_MS = 320 ms`（背景事件，慢一点），
唤醒 `IDLE_WAKE_MS = 120 ms`（要即时响应）。动画中途再碰会从当前透明度反向，
不会有跳变。录屏抽帧实测淡出 `255 → 223 → 196 → 158 → 133 → 124`，约 330 ms，与设定吻合。

> 用 `adb shell screenrecord` 录 8 秒再 `ffmpeg -vf fps=15` 抽帧，是唯一靠谱的验证方式：
> `screencap` 单张要几百毫秒，根本抓不到 300 ms 的动画。注意 Git Bash 会把 `/sdcard/...`
> 转换成本地路径，要加 `MSYS_NO_PATHCONV=1`。

## 拖动改成自由位置

原来的 `SNAP_LOW 0.34` / `SNAP_HIGH 0.66` 把水平位置硬切成左、中、右三档，手指停在边缘附近
松手会被拽过去，用户反馈手感奇怪。现在松手就留在原地，只保留一条：拖到离底部 8% 以内
（`DOCK_THRESHOLD 0.92`，原来是 0.80）才停靠，停靠后贴底并居中。

验证：从中间拖到 `x=450` 松手，卡片左边缘停在 62，旧版会吸到 0；再拖到最底部，卡片贴底并回到居中。

## 长按触发拖动

按下不再直接拖，要按住 `DRAG_LONG_PRESS_MS = 380 ms` 才算数，触发时 `performHapticFeedback(LONG_PRESS)`
给一次震动。手指在 380 ms 内移动超过系统 touch slop 就取消长按，快速划过胶囊不会把键盘带跑。

拖动起点锚在**手指当前位置**而不是最初按下的点，否则长按识别出来的那一刻卡片会突然跳一下。

验证：快速划（300 ms）键盘不动；按住 1 秒再拖，卡片跟手上移并且在原处停住；
`adb logcat | grep Vibrator` 能看到振动调用。注意用 `input swipe` 测不了长按拖动——
它一上来就移动、立刻被当成划动取消，要用 `input motionevent DOWN` + `sleep` + `MOVE`。

## 四角缩放

`FloatingKeyboardCorners` 是盖在整张卡片上的一个 overlay，四角各画一个 9 dp 方块，
命中区 38 dp 见方。它没有拆成四个小 View 是因为按到空白处的 `ACTION_DOWN` 可以直接
`return false`，事件由父容器交给下面的键盘，卡片除四角外仍然是键盘。

拖角时对角**在屏幕上固定**：缩放 pivot 是 `(width/2, height)`，直接改 factor 会让四个方向
一起动，所以靠 translation 补偿 —— `tx = tx0 + (锚点view内坐标 - pivot) * (factor0 - factor)`。
factor 用「手指到锚点的距离 ÷ 按下时的距离」乘上起始 factor，斜着拖也跟手。

松手后把 `scale` 和位置 fraction 一起写进偏好，下次弹出保持。满宽（factor ≥ 1）时
手柄和角块全部移除。

### 踩到的坑

- **`applyInsets` 每帧都会把 scale 冲掉**：它从偏好读 factor 再 `applyScale`，而松手才写偏好。
  拖动期间偏好还是旧值，于是每一帧都把现场改回去，表现为「拖了没反应、松手还是原大小」。
  `applyScale` 里加了 `if (scaling) factor = appliedScale;`，按住期间以手指为准。
- **`setElevation` 不改变触摸分发顺序**，只影响绘制和阴影。overlay 能先收到触摸靠的是
  `addView` + `bringToFront`（子 View 里排最后的分发优先级最高）。
- 测试时别用固定坐标：每次拖动后卡片位置都会变。临时在 `ensureCorners` 里打印
  `getLocationOnScreen` 的屏幕坐标，按日志里的角块位置去 `input swipe`，测完删掉日志。

### 悬浮和单手模式完全互斥（2026-11-24 用户决定）

用户实测：悬浮状态下再开原生单手模式，两边各自算宽度和位置，叠加后键盘形状直接错乱。
结论是这两个功能**完全互斥，开一种就取消另一种**，不用去调和它们的叠加。

实现时要注意：

- 单手模式的偏好在 `pref_key_one_handed_mode`，`normal` 之外的值就是开着。
- 悬浮生效前先看这个值，不是 `normal` 就不悬浮（或先关单手再悬浮），不能两个一起算。
- 反过来开单手时，悬浮要退出并回到 docked，否则 insets 会打架。
- 具体是先改偏好还是只让悬浮让路，实现的时候再定；原则是任何时刻只有一个生效。

## 编辑态落地（`FloatingKeyboardEdit`）

原型定稿后在 `patches/java/com/google/android/inputmethod/pinyin/FloatingKeyboardEdit.java` 落地，
测试包 `...floatingtest` 上逐项验过：入口、外观、拖动、缩放（含屏幕边界）、复位、退出。

### 入口

胶囊上双击，第二下按住 300 ms（`ENTER_EDIT_MS`）切进编辑态。双击判定窗口
`DOUBLE_TAP_MS = 320 ms`，即第二下必须在上一手抬起后 320 ms 内落下，按系统双击超时取的。

第一下抬起后先挂长按计时器，第二下按下时才换成编辑计时器，所以双击失败仍然退化成普通长按拖动，不会卡住。

### 外观

- **直角**。用户明确要求：键盘是直角的，编辑态也是直角，不做圆角。描边和半透明覆盖层都用 `drawRect`。
- 按键压到四成：`0x73FFFFFF`（45% 白）盖住整张卡片，按键和候选栏一起变淡。
- 四角 L 角标 13 dp，线宽 3.5 dp。
- 中心实心圆 130 dp 带白色四向箭头；左侧浅色圆复位，右侧浅色圆退出。
- 全部颜色取自键盘主题色，只有一个强调色。

### 主题色不能读 `colorAccent`

`colorAccent` 在这个应用里恒为 `#4DB6AC`（teal），换绿色、蓝色主题都不变，照它画出来的编辑态永远是一套青色。
原生悬浮编辑界面跟着主题走，说明它从别处取色。

view 上也读不到：按键是 `Canvas` 自绘的，`getBackground()` 不是纯色 drawable，
`getBackgroundTintList()` 和 `ImageView` 的 `getImageTintList()` 都是空，扫遍整棵树候选数是 0。

最后改成**把键盘画进 bitmap 再采样**：

```java
Bitmap bitmap = Bitmap.createBitmap(w, h, ARGB_8888);
area.draw(new Canvas(bitmap));
// 每 3px 采一次，按 HSV 饱和度 × 亮度打分，取最高分
```

键盘上饱和的东西只有回车键和搜索键，取到的就是主题 accent。
实测绿色主题得 `#4DB6AC`，当前蓝色主题得 `#4285F4`，和键盘上那颗搜索键完全同色。
只在进编辑态时做一次，可以接受。

### 缩放要卡在屏幕内

锚定角固定、往拖动方向长，所以可达的最大 factor 由锚点到屏幕边的余量决定：

```java
float roomX = (corner == 1 || corner == 2) ? decor.getWidth() - anchorX : anchorX;
float roomY = (corner == 2 || corner == 3) ? decor.getHeight() - anchorY : anchorY;
float limit = Math.min(roomX / area.getWidth(), roomY / area.getHeight());
factor = Math.max(MIN_SCALE, Math.min(factor, limit));
```

实测把右上角往屏幕外拖，卡片右边缘停在 1079（屏幕 1080），不会越界。

### 验证方式

`input motionevent` 是唯一能测双击的通道，而且**坐标必须每轮重新量**：键盘位置和缩放都会变，
按上一轮的坐标点过去只会点空、日志一条都没有。

```bash
adb shell "input motionevent DOWN X Y; input motionevent UP X Y; \
           input motionevent DOWN X Y; sleep 0.5; input motionevent UP X Y"
```

两次 down 之间不能加 `sleep`，加了间隔就超过 320 ms 判定失败；连着写两条命令的间隔约 100–150 ms，能过。

量卡片位置按描边颜色找边界最稳（描边就是主题色），命中的圆钮半径只有 26 dp 左右，
卡片位置一变就得重量坐标，点偏一点就完全没反应。

## 悬浮键盘的设置项与快捷菜单

设置页「外观与布局」的顺序改成了：主题 → 单手模式 → 悬浮键盘 → 待机时自动透明 → 键盘高度。
悬浮开关从单手模式上面挪到了下面，新开关紧随其后。

### 待机时自动透明

偏好键 `idle_fade`，默认开。它是独立的一个键，不是从 `enabled` 推导出来的：
关掉悬浮再打开，这里选的仍然是上次的值，只是不生效。界面上的联动只做到「悬浮关着时这一行置灰」，
值本身不改。

实测两种状态：关着时不淡，键盘区平均亮度 240；打开后等 8 秒淡到半透明，亮度 135。

### 互斥

两个方向都已经在 `ModernSettingsActivity` 里：开单手模式会把悬浮关掉，开悬浮会把单手模式重置为关闭。
本轮只是把新开关接进了同一条链路，互斥逻辑没改。

### 快捷菜单里的单手按钮

悬浮生效时把工具栏里那三个单手相关按钮设成 `GONE`，关掉悬浮时恢复。

**这三个按钮的 contentDescription 不是 `one_handed_access_point_content_desc`。**
那个字符串的值是「单手模式」，但它标的是面板入口，从来看不到。实际在树上的是：

| 资源名 | 中文 |
| --- | --- |
| `left_handed_content_desc` | 切换到左手键盘 |
| `right_handed_content_desc` | 切换到右手键盘 |
| `expand_keyboard_content_desc` | 退出单手模式 |

哪几个存在取决于当前是不是单手模式，所以三个都要匹配。

**这一条没能在当前设备上直观验收。** Qwerty 布局下这个工具栏本来就不出单手按钮：
装上没有这段代码的 f35 对照，同样状态下菜单里也没有，所以看不到隐藏前后的差别。
代码按描述匹配实现，逻辑本身在日志里验过（三个资源都能取到、遍历确实跑到了工具栏），
但要真看到效果得用会显示这个按钮的布局。

### 实现上必须注意的

- **不能在 insets 计算里直接改可见性。** `onComputeInsets` 跑在布局流程里，
  子 view 翻 `GONE` 会当场再要一次布局。改成 `decor.post()` 到下一轮消息，
  再用**时间戳**节流（50 ms）。不要用「pending 标志」：post 万一没跑，标志就永远卡住，
  关掉悬浮后按钮再也不会回来。
- 工具栏是懒创建、展开时重建的，只在 insets 那次扫一遍会扫空。
  挂 `OnGlobalLayoutListener` 才能抓到重建，但要节流到 500 ms —— 卡片的把手每帧重写 bounds，
  布局回调一直在响，不节流就是每帧遍历整棵树。

### 工具栏里那个「文本编辑」入口没做成

需求是悬浮模式下把快捷菜单里「主题」和「设置」中间那个入口（`ic_access_point_text_editing_dark_theme`）藏掉。
试了十来版，全部失败，原因值得记下来。

**这个按钮没有任何稳定标识。**

- 所有工具栏图标共用一个资源 id `id/icon`（`0x7f0f0057`）
- 它没有 contentDescription。另外三个单手按钮有，所以那几个能按描述藏，这个不行
- 图标被包在一个混淆的自定义 drawable 里，`getIntrinsicWidth()` 返回 42/63 这种包装后的值，
  `getConstantState()` 和目标资源的 `BitmapDrawable$BitmapState` 永远不相等
- `AccessPointsBar` 的 `getChildCount()` 只有 2（一个背景加一个 item），不是一整行按钮
- 按 view 树遍历顺序取索引会拿到齿轮；按屏幕 x 排序取索引虽然第一轮对，但 GONE 之后重排，
  下一轮会连锁把后面的图标也吃掉

试过的方案：

| 方案 | 结果 |
| --- | --- |
| 按 contentDescription 匹配 | 描述是 null |
| `id/icon` + 遍历顺序取索引 2 | 隐藏了齿轮 |
| drawable `ConstantState` 比较 | 永远 false，被包装过 |
| 按 `getIntrinsicWidth()` 筛选 | 目标 58，实际图标 42/63，对不上 |
| y 聚类找行 + x 排序取索引 3 | 第一轮对，重复扫描连锁隐藏 |
| 同上加「已有隐藏就跳过」判断 | 一次都没隐藏成功 |

**下一步可行的方向**（都需要更深的工作，本轮没做）：

1. 改 ImeDef 元数据：那个入口是不是 AccessPoint 由 `metadata/*.binarypb` 决定，
   悬浮生效时就不让它出现
2. 在 `AccessPointsBar` 的 smali 里加一个极小钩子，把 item 的 AccessPoint id 暴露给 Compat 类，
   再由 Compat 精确匹配 `id_access_point_textediting`

第二条和项目「钩子 + Compat 类」的既有做法一致，代价是要改原生 smali。

### 逆向到的结论（从这里接着做）

那个入口的 AccessPoint id 是 `access_point_textediting`，图标是
`ic_access_point_text_editing_dark_theme`。组件入口在 `AccessPointsBar`：

- **`AccessPointsBar.a(List<aon>)` 是唯一把列表变成按钮的地方**：方法里遍历列表，
  每个 `aon` 取 `Lavb;->a(Laon;ZZ)` 生成 `SoftKeyDef`，塞进新建的 `SoftKeyView`，
  再按 `aon.a`（id 字符串）存进内部 `Lkx`（id → view 的映射）。
  调用者只有两个：`ahm.smali:337` 和 `AccessPointsManager.smali:1290`。
- **`aon.a:Ljava/lang/String;` 就是那串 id**，由构造方法从 `Laoo;->a:Ljava/lang/String;` 拷来。
  `aon` 没有覆写 `toString()`，反射或 `toString()` 都拿不到，只能在 smali 里 `iget-object` 直接读字段。
  混淆名在本版本固定（打补丁针对 4.5.2），不会自己变。
- `AccessPointsBar.getChildCount()` 只有 2 是因为它带 `c:I` 这个尾部占位，
  按钮是按索引 `addView(v0, v5)` 插进去的，遍历子 view 数不出真实项。

**因此实现路线（下次直接做）**：

1. `FloatingKeyboardCompat` 加一个纯判定：
   `shouldHideAccessPoint(String id, Context context)`，悬浮生效且 id 是 `access_point_textediting` 时返回 true。
2. 在 `AccessPointsBar.a(List<aon>)` 的 `.prologue` 之后插一段倒序循环：
   读 `Laon;->a`，交给上面的方法判定，命中就 `List.remove(i)`。
   倒序删才不会错位。寄存器用 v9–v11，同时把 `.locals 9` 改成 `.locals 12`。
3. 钩子只负责「取字段 + 转调」，判定全在 Compat 里，符合既有做法。

将来「快捷入口用户自定义」也挂同一个点：把固定 id 换成用户选定的保留集合即可，
不用再动一层递归。

### 关键：先打坐标，再对截图

和截图对齐后顺序是：主题(0)、单手(1)、设置(2)、文本编辑(3)。上轮藏 2 掉齿轮、藏 3
掉单手，正好对上，说明普通模式和悬浮模式共用同一套位置。

**这里的映射一开始认反了。** 靠图标外形判断不可靠：中间那个方框里画着一只手，看着像
文本编辑，实际点下去是把键盘缩到左边——那是单手模式；反而是 `<I>`（左右箭头夹竖线）
点开才是文本框，带选择、复制、粘贴、全选。判断依据只能是点开看，或者用
`dumpBars` 打出的 id 顺序，别看图标长什么样。

### 还有一处绕了远路

一直以为悬浮模式早就开了，其实之前那些截图全是普通键盘。悬浮的卡片和普通键盘的工具栏
长得像，只有点开菜单后才知道是哪个。`isEnabled` 判的是悬浮开关，所以前几轮改的效果
一直没被验证过。

悬浮卡片的位置也和普通键盘不同：`>` 在屏幕 y 约 1700，而普通键盘的 `<` 在 y 约 1590。

### 最终做法

`AccessPointsBar.onLayout` 里调 `FloatingKeyboardCompat.syncFloatingToolbar(bar)`：

1. 读悬浮开关状态，`isEnabled`
2. `bar.post(...)` 等绑定完成
3. 把第 3 个 key（单手模式）的可见性设成 `GONE` 或 `VISIBLE`

**关掉悬浮时要显式设回 `VISIBLE`**，否则隐藏是持久的，切回普通键盘也恢复不了。
这一点第一版漏了，验证时发现普通键盘也少了两个图标。

### 验证结果

| 悬浮开关 | 菜单项 |
| --- | --- |
| 开 | 收起、主题、设置、文本编辑、更多（5 个） |
| 关 | 收起、主题、单手、设置、文本编辑、更多（6 个） |

两个方向都截图确认过。**只隐藏单手模式，文本编辑保留**——单手和悬浮卡片互斥，留着
会自相矛盾；文本编辑在卡片里照常能用。

## 快捷入口自定义：先试原生偏好这条路

目标是让快捷菜单里的入口能开关、能排序，以后加新入口也方便。先试了最小的那条路：
看原生有没有现成的偏好可以写。

### 原生确实有

偏好 key 是 `pref_key_access_points_showing_order`，值是一串用分号隔开的入口 id。
`AccessPointsManager.b(I)V` 读它：有值就按字符串切分，没值就退回 `arrays.xml` 的
`access_points_order` 数组。切出来的清单同时决定**顺序**（列表顺序）和**开关**（在不在里面）。

入口一共 7 个，id 就是各自的字符串值：

```
access_point_search         access_point_sticker
access_point_theme_setting  access_point_one_handed
access_point_settings       access_point_textediting
access_point_translate
```

默认数组里只有前 5 个，`textediting` 和 `translate` 不在其中，是运行时补进去的。

### 实测下来的三个问题

写了探针把偏好改成只剩主题和设置，然后重启键盘看效果：

1. **原生会往偏好里追加条目。** 写完是 `theme;settings`，下次读回来变成
   `theme;settings;one_handed;textediting`。也就是说这个偏好不完全归我们管，原生也会往里写。
2. **改偏好不会立即生效。** `AccessPointsManager.onSharedPreferenceChanged` 只监听
   `pref_key_enable_one_tap_to_search` 这一个 key，改顺序偏好得靠重启键盘才生效。
3. **改完出现过设置入口消失。** 偏好里明明有 `access_point_settings`，界面上就是不显示，
   卸载重装清掉偏好才恢复。说明渲染时它被 `kx` 里查不到记录而跳过了，这条路上还有别的条件。

### 结论：这条路不够，走自建

即使把上面三个问题都绕过去，这条路**上限也只能配置原生已有的那 7 个入口**。想加一个
原生没有的快捷方式，这里没有任何位置可以加——而「以后自己加新入口」正是这次要做的事。

所以要自己实现一套工具栏。原生这套调研没有白做，入口 id、图标、点击动作的位置都清楚了，
自建时可以直接照着接。

## 自建工具栏：第一版骨架跑通

原生那条路走不通，改成自己做。第一版只放主题和设置两个入口，目的是验证骨架，不是功能完整。

### 做法

新增 `patches/java/.../QuickBar.java`，入口表就是里面一个数组：

```java
private static final Entry[] ALL = {
        new Entry("theme", "ic_access_point_theme_setting_dark_theme", "主题", ACTION_THEME),
        new Entry("settings", "ic_access_point_setting_dark_theme", "设置", ACTION_SETTINGS),
};
```

加新入口就是往这里加一行，图标按 drawable 资源名查，点击动作自己实现。

挂在原来的位置：`AccessPointsBar.onLayout` 里调用 `QuickBar.attach`，把原生条目全部设 `GONE`、
清掉背景，然后在同一个父容器里插入自建的一行。

**原生那个 bar 本身不能设 `GONE`。** 它一旦不参与布局，外层就不再走 `onLayout`，我们唯一
的同步时机就没了。只能清空它的内容，保留它占位。

### 踩到的三个点

1. **`javac` 按 GBK 读源码。** 中文注释直接编译失败（`编码 GBK 的不可映射字符`）。这个项目的
   Java 源码注释一律用英文，就是因为这个。新文件里写中文注释会挂。
2. **布局参数不能自己 new。** 父容器是 `LinearLayout`，塞 `FrameLayout.LayoutParams` 会崩。
   改成 `parent.addView(view, index)` 让父容器生成参数，再改宽高。
3. **图标只有深色主题那一版**（`_dark_theme`，本身是浅色）。背景是浅色时要用
   `textColorPrimary` 着色，不能直接用资源原色。

### 现在的样子

悬浮模式下展开菜单：收起、主题、设置、更多，四个图标排布和原生一致，点主题能打开主题选择页。

### 下一步

- 把单手和文本编辑接进来（这两个动作要调原生能力，比跳转难）
- 设置页做开关和排序，配置存 Preferences
- 配置生效后，`HIDDEN_TOOLBAR_KEYS` 那套按下标隐藏的逻辑可以整个删掉

## 接单手和文本编辑：没成，回滚了

自建栏骨架能显示能跳动，接着要把单手和文本编辑也接上。这两个不是跳页面，得借原生的
动作链路，试了一版没成，已经回滚。

### 搞清楚的机制

原生的入口点击最终落到 `GoogleInputMethodService` 的一个 `sparse-switch` 上，三个自定义
keycode：

| keycode | 十进制 | 去向 |
| --- | --- | --- |
| `-0x275c` | -10076 | `AccessPointsManager.a(Event, true)` |
| `-0x275d` | -10077 | `AccessPointsManager.a(Event, false)` |
| `-0x275e` | -10078 | 置位后走 `KeyData` 分支 |

按钮本身由 `AccessPointsPanel` 用 `avb.a(aon, Z, Z)` 转成 `SoftKeyDef`，动作是「PRESS +
keycode + 入口 id」。

### 试的思路

原生按钮虽然被藏起来，但监听器还挂着，所以自建图标被点击时可以 `performClick()` 转发过去，
动作链路完全走原生。为此在 `AccessPointsPanel.a()` 里加钩子，把 `id → view` 存下来。

### 卡在哪

1. **注册时机靠不住。** `AccessPointsPanel.a()` 只在面板布局时调用，重装后第一次展开菜单
   那一刻原生条目还没注册，点下去没反应。
2. **布局和原生条目打架。** 自建栏用 `MATCH_PARENT` 会挤掉原生的「更多」按钮；改成
   `WRAP_CONTENT` 之后 `weight` 失效，图标被压成 0 宽；换固定宽度后，原生条目有时没能
   全部藏住，两边叠在一起。

### 下次从这里接

转发这条路本身是通的，问题都在时机和布局上。可以试：

- 把 `id → view` 的登记挪到更早的时点，或者在自建栏点击时**当场**去原生栏里按顺序找按钮，
  不要依赖提前注册
- 自建栏不要挤在同一行里和原生按钮抢宽度，考虑接管整行（连「更多」一起自己画）

代码已回滚到骨架那一版，设备上装的是 `floating-ch.apk`：主题、设置两个入口，显示和跳转正常。

## 展开按钮失效：根因是 smali 钩子写坏了类名

上一节把展开按钮点不动归到几处猜测上，全猜错了。真因在日志里：

```
java.lang.VerifyError: Verifier rejected class
com.google.android.apps.inputmethod.libs.framework.keyboard.widget.AccessPointsPanel:
void ...AccessPointsPanel.a() failed to verify: [0x49] 'this' argument
'Reference: ...keyboard.SoftKeyView' not instance of
'Unresolved Reference: com.google.android.inputmethod.libs.framework.keyboard.SoftKeyView'
```

`decoded` 里的 `AccessPointsPanel.smali` 有一行 `invoke-virtual` 把类名写成了
`Lcom/google/android/inputmethod/libs/framework/keyboard/SoftKeyView;`，**少了中间的 `apps`**。
这个类根本不存在，verifier 直接拒绝整个 `AccessPointsPanel`，于是 `AccessPointsManager.a()`
一调就崩，展开动作永远走不完——按键有按压反馈，但菜单不出来。

来源是加 `registerNativeItem` 钩子时把插入锚点写错了，后来撤销钩子时又把那行坏类名原样写了回去。
改回 `Lcom/google/android/apps/...` 一处，展开立刻恢复。

### 教训

**插 smali 钩子时，锚点必须逐字复制原文，不能手打。** 这次是手打锚点，`apps` 段漏掉，
错误被带进产物，还被后续几次构建继承下来，白白折腾了好几轮构建。类名对不对，构建不会报，
只有运行期 verifier 才会拒绝，所以必须在装机后看 `logcat` 的 `VerifyError`，不能只凭界面现象猜。

## 键盘读不到设置页的配置

3. **只在创建时读。** `attach` 里原来一旦找到自己的行就直接返回，配置改了不会重建。改成

### 下次先做这个

### 顺带清掉的

## 接管范围：不该绑定悬浮开关

自建工具栏原来只在悬浮键盘开启时接管，悬浮关掉就退回原生。这是我当初把
`QuickBar.attach(nativeBar, selfEnabled)` 的第二个参数直接接了 `isEnabled`（悬浮开关）造成的，
和「接管所有键盘形态」的设计目标相反。

已改：`attach` 去掉这个参数，`syncFloatingToolbar` 无条件调用，顺带删掉恢复原生那条分支。

### 现在卡在哪

改完之后**普通键盘（悬浮关闭）下仍然没有接管**，展开还是原生那四个，不受设置页配置控制。
悬浮开启时接管正常。

加了一条 `Log.e` 在 `attach` 入口，悬浮和普通两种情况下都**没有任何输出**，说明 `attach`
在普通键盘下根本没被调用。那么问题不在 `attach` 内部的条件判断，而在更上游：

1. `AccessPointsBar.onLayout` 在普通键盘下有没有执行
2. 执行了的话，`bar.post(...)` 的 runnable 有没有跑（bar 那一刻可能还没挂到窗口上）
3. 普通键盘的入口条是不是另一个实例（不是 header 里那个 `AccessPointsBar`）

下次从这三条查，先在第 1 条上加日志确认，不要直接改 `attach`。

## 普通键盘不接管：钩子没执行

上一节列的三个待查方向，第一条就有结论了。

### 取证过程

`logcat` 这条路先被排除：这台设备上**输入法进程没有输出任何自己打的日志**（348 条相关记录
全是系统服务替它打的）。所以「日志没出来」不能证明代码没执行。

改用写文件追踪：在 `syncFloatingToolbar` 和 `attach` 入口各追加一行到应用私有目录，用
`run-as` 读。结果：

- 追踪字符串确实进了 dex（`quickbar-trace.log`）
- **普通键盘下追踪文件根本没被创建**

所以 `syncFloatingToolbar` 在普通键盘下确实没被调用，不是条件判断挡掉的。

### 定位

钩子挂在 `AccessPointsBar.onLayout` 里（`floating_toolbar_patches.py` 加的，解码产物里能看到
第 933 行的 `invoke-static`）。既然普通键盘下它没跑，说明**普通键盘的入口条不是 header 里那个
`AccessPointsBar` 实例**，或者是同一份布局的另一个实例、另一条渲染路径。

`AccessPointsViewHelper` 持有 `AccessPointsBar` 字段（`->a`），下一步从这里查：它是在
`findViewById` 取的，还是自己 inflate 的；普通键盘的 header 走的是哪份布局。

### 教训

**在这台设备上排查输入法，不要用 logcat 当天条。** 没有输出不等于没执行，先找一个确定会跑的
地方做对照，或者直接落到文件。

## 找到挂点：普通键盘下 onLayout 永远不跑

根因查清了，和我之前的猜测都不一样。

**`AccessPointsBar` 在普通键盘的 header 布局里是 `visibility=gone`**（`styles.xml` 里
`AccessPointsBar` 这个 style 写着 `<item name="android:visibility">gone</item>`）。
GONE 的 view 不参与布局，所以挂在它 `onLayout` 上的钩子**永远不会被调用**——不是条件挡掉的，
是那个方法根本不跑。悬浮键盘能用，是因为展开提示层里那个 bar 是可见的。

### 换挂点

普通键盘的条目是运行时灌进 `access_points_overlay_view` 的（bar 自己只是 GONE 的占位），
所以钩子改挂 `AccessPointsBar.a(List)I` 的开头——条目被设置时触发。原来 `onLayout` 那个保留，
覆盖悬浮那条路径。

同时三处配套改动：

1. `attach` 的判断从「bar 可见」改成「bar 有条目」（`getChildCount() > 0`），因为 bar 本来
   就不可见
2. 容器改成先找 `access_points_overlay_view`，找不到才退回 bar 的父容器——普通键盘下 overlay
   是 bar 的兄弟，不是父子
3. `hideNativeEntries` 改成按容器清理，跳过语言键和自建行

### 现在的状态

普通键盘下**原生四个入口已经被隐藏**（展开后只剩展开按钮和收起按钮），说明 `attach` 确实执行了。
但**自建行没画出来**，那一行是空的。

下一步查：`overlay.addView` 有没有成功、overlay 的尺寸是不是 0、栏里的按钮有没有拿到宽度。
按这轮的经验，先看这三样再动代码。

## 普通键盘接管：查到根因，但没做通

这一轮把根因挖到底了，也试到了能看见失败现场的程度，但最终没能收敛，代码回滚到可用状态。

### 根因

`AccessPointsBar` 在普通键盘的 header 里是 **GONE**（`styles.xml` 的 `AccessPointsBar` style
写死 `android:visibility=gone`）。GONE 的 view 不参与布局，挂在它 `onLayout` 上的钩子永远不跑。
悬浮键盘能用，是因为展开提示层里那个 bar 是可见的。

### 试过的做法

挂点改到 `AccessPointsBar.a(List)I`（条目被灌进去时），配合三处改动：判断从「可见」改成
「有条目」、容器改成先找 `access_points_overlay_view`、`hideNativeEntries` 按容器清理并跳过
语言键。

**效果**：普通键盘下原生四个入口确实被隐藏了，说明挂点和执行路径都是对的。但自建行量出来是
**0 宽**，展开后是一条空带。

### 追踪拿到的现场数据

在 `attach` 里写文件（logcat 在这台设备上不可信）：

```
before add overlay=LinearLayout 975x105 kids=2 entries=1
after add size=0x0 kids=3 childKids=1
posted bar=0x0 vis=0 overlay=975x105
  [0 SoftKeyView 0 204x105]
  [1 SoftKeyView 0 204x105]
  [2 LinearLayout 0 0x0]     ← 自建行
```

overlay 有 975x105 的空间，自建行加进去了（kids 2→3）、里面有 1 个按钮，但自己量成 0x0。
`requestLayout` 无效；把 `MATCH_PARENT` 改成 `weight=1 + width=0` 也无效。

### 顺带修掉的一个真问题

加追踪时引入了一个匿名 `Runnable`，生成 `QuickBar$2.smali`，但 `apply_patches.py` 只拷固定的
三个文件名，类找不到被 `catch` 吞掉，`attach` 静默失败。已改成按 `QuickBar*.smali` 通配整批
拷贝——**以后再加匿名类不会再踩这个坑**。

### 下一步该换个思路

不要在 `access_points_overlay_view` 里塞 LinearLayout 了。那是个横向容器，普通键盘下它对子
view 的测量行为和我们期待的不一样，两次调参都没影响结果，说明问题不在宽度参数上。可以考虑：

1. 接管 header 那一层的 `FrameLayout`，自建行作为绝对定位的覆盖层，不参与 LinearLayout 的分配
2. 或者干脆不用 overlay，把 bar 从 GONE 改成可见，让它自己布局，再往它里面塞我们的行
3. 或者放弃复用原生容器，自己 inflate 一份 header

代码已回滚到 `58cedb9`：普通键盘保持原生（四个入口正常），悬浮键盘走自建行。

## 方案一（覆盖层）试了，也没通

按上一节的思路：自建行不再塞进 `access_points_overlay_view`，而是往上找到 header 的
`FrameLayout`，用 `FrameLayout.LayoutParams` + margin 定位，精确盖在入口区上面，并挂
`addOnLayoutChangeListener` 跟随它的位置。同时把挂点保留在 `a(List)I`。

### 结果

普通键盘展开后仍然是空条。最后一次加追踪想拿数据，追踪文件根本没生成，说明 `attach` 在
拿到尺寸之前就早退了——要么 `entries.getChildCount() == 0`，要么 `overlayOf` 返回 null。
**没拿到证据就停了**，不再往下猜。

### 这轮学到的

1. **`overlay.getParent()` 是那个横向 `LinearLayout`**，不是 FrameLayout。我第一次改的时候
   直接用 parent 当宿主，等于没改。找宿主必须往上走，直到遇到 FrameLayout。
2. **匿名类必须能被补丁脚本拷到**。`apply_patches.py` 原来只拷三个固定文件名，我加匿名
   `Runnable` 后 `QuickBar$2.smali` 没被拷贝，`attach` 抛 `NoClassDefFoundError` 被 `catch`
   吞掉，表现就是「什么都没发生」。已改成按 `QuickBar*.smali` 通配整批拷贝，这个修复保留。

### 下次接手

先只解决一件事：**`attach` 在普通键盘下到底走到哪一步**。在方法开头、`overlayOf` 之后、
`frameHost` 之后各写一行追踪，三行就能定位早退点。拿到再改代码。

如果 `overlayOf` 就是返回 null（`getIdentifier` 在运行时拿不到那个 id，或者 bar 的 parent
不是 header），那就说明这个挂点的前提本身不成立，得换更根本的做法：自己 inflate 一份
header，不碰原生那套容器。

## 转向：废掉自建行，改原生

自建栏小毛病太多，用户决定放弃，回归原生。目标收窄成两条：**控制原生快捷入口的开关和顺序**，
暂不追加自定义入口。设置页保留，改用来驱动原生。

### 已经通的

`AccessPointsManager.b(I)` 从 `access_points_order` 读出 id 列表，存进 `->a:Ljava/util/List;`
（纯字符串）和配套的 `->a:Ljava/util/Set;`。在方法收尾的 `:cond_3` 挂了钩子，交给新的
`AccessPointsOrder.apply(Context, List, Set)` 原地过滤重排。

追踪证明这段确实生效：

```
apply ids=[access_point_search, access_point_sticker, access_point_theme_setting,
           access_point_one_handed, access_point_settings]
      raw=access_point_one_handed:0|access_point_textediting:0|
          access_point_theme_setting:1|access_point_settings:0
applied -> [access_point_theme_setting, access_point_search, access_point_sticker]
```

### 没通的

**屏幕上仍然是 4 个入口，不受这个列表影响。** 说明 bar 渲染用的不是
`AccessPointsManager->a:Ljava/util/List;`，而是另有来源。

线索：`Laon;->a:Ljava/lang/String;` 就是入口 id，`AccessPointsManager.a(Laon;)V` 把
id → Laon 存进 `->a:Lkx;`（map）。注册这两处的是 `GoogleInputMethodService` 和
`ExtensionManager`，都是独立往 map 里塞，不看那个 List。所以 List 可能只管拖拽排序的参考顺序。

**下一步**：把过滤挪到真正决定渲染的地方，也就是 `AccessPointsBar.a(List<I>)I`（设置 items
的那个方法）。那里的元素是 `Laon`，id 在 `Laon->a`。因为不能反射、也不想在 Java 侧引用混淆
类名，过滤得在 smali 里做：遍历列表、读 `Laon;->a:Ljava/lang/String;`、跟配置比对、拼新列表。

### 顺带

`AccessPointsOrder` 一开始写成包内可见，跨包调用直接 `IllegalAccessError` 崩在

## 原生快捷入口：机制摸清了，功能做通了

自建行废弃后，改在原生 `AccessPointsManager` 上做。这一轮把整条链路逆向完整了，功能也验证通过。

### 三份状态

`AccessPointsManager` 用三份数据描述入口：

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `->a:Ljava/util/List;` | List | 顺序，元素是 id 字符串（`access_point_theme_setting` 这种） |
| `->a:Ljava/util/Set;` | Set | 已注册过的 id，会被渲染遍历当作白名单 |
| `->a:Lkx;` | Map | id → 条目对象（`Laon`，其 `->a` 字段就是 id） |

### 渲染链路

`AccessPointsManager.a(Z)V` 是整理渲染数据的地方：

1. 遍历 `->a:List`（顺序）
2. 查 `->a:Set`，不在集合里的跳过
3. 从 `->a:kx` 取条目，取不到跳过
4. 依次加入 `->b:List`（最终显示列表）
5. 交给 `AccessPointsViewHelper` → `AccessPointsBar.a(List)`

### 为什么初始化时改会被覆盖

`->a:List` 的来源是 `res/values/arrays.xml` 的 `access_points_order`（search、sticker、
theme、one_handed、settings 五个）。构造时 `b(I)` 把它读进列表。

但 `AccessPointsManager.a(Laon;)V` 在注册每个入口时（`.line 131-133`）会做：

```
if (!List.contains(id)) { List.add(id); Set.add(id); }
```

**追加到末尾。** 所以只在 `b(I)` 里重排一次，之后运行时注册的 `textediting` 等又会被追加回去。
实测追踪到重排后的三个 id 又变回六个。

### 最终做法

两个挂点，都调 `AccessPointsOrder.apply(Context, List, Set)`：

1. **`a(Z)V`（渲染整理）开头**。每次重建显示列表前重排，作为兜底。
2. **`a(Event;Z)V`（展开/收起）开头**。渲染那次刷新只在切换键盘时发生（`setKeyboardView`），
   挂在这里才能改完设置立刻生效。

`apply` 的规则：配置里开启的按配置顺序排在前面，配置没提到的保持相对顺序跟在后面，配置里明确
关闭的从列表和集合里剔除（集合只 `removeAll` 禁用项，不清空——里面还有 `more_access_points`
这种非入口 id）。

### 验证结果

- 开关：4 → 3 → 2 → 1 逐个验证，条形图同步变化
- 排序：把「设置」上移后，齿轮确实跑到调色板前面
- 即时生效：改完设置切回键盘就变，不需要重启输入法
- 注入点在 manager 层，与键盘形态无关，悬浮和普通键盘共用同一条链路

### 踩过的坑

`AccessPointsOrder` 一开始写成包内可见，跨包调用直接 `IllegalAccessError` 崩在
`AccessPointsManager.b(PG:52)`。这类 Compat 类必须 `public`，被 smali 调用的方法也要 `public`。

## 「开了三个只看到一个」：是残留状态，不是过滤错

### 先查掉的误判

用户开了主题、文本编辑、设置三个，键盘上只出现主题。逐个排查：

- `apply` 算得对：`in` 是原生六个，`out` 是 `[theme, textediting, settings]`
- `known`（白名单集合）里三个 id 都在
- `map`（id → 条目）里 `settings`、`theme_setting`、`textediting`、`one_handed`、
  `more_access_points` 也都在

**所以链路本身没问题。** 差别在键盘形态：同一份配置在悬浮键盘下显示三个，在普通键盘下只显示一个。

### 真正的原因

普通键盘展开入口时**不会触发重排**。那个 `a(Event;Z)V` 钩子只在悬浮卡片那条路径上被调到，
普通键盘下改完设置再展开，用的是上一次的结果，所以停在旧状态。

重启输入法之后普通键盘同样正常显示三个。也就是说这是**刷新时机**的问题，不是过滤逻辑的问题。

### 顺带确认 search / sticker 为什么看不见

`map` 的键里根本没有 `access_point_search` 和 `access_point_sticker`——这个机型上它们压根没注册，
所以无论配置怎么开都不会出现。已按用户要求从设置页移除，catalog 回到四项：主题、单手、文本编辑、
设置。

### 还欠的

普通键盘下改完设置要切一次键盘（或重启输入法）才生效。悬浮键盘下是立刻生效的，因为那个钩子
覆盖到了。要补的话得找到普通键盘展开的那条路径，把重排也挂上去。

## 查证：普通键盘其实也是即时生效的

上一节留了个疑问：普通键盘下改完设置是不是要切键盘才生效。实测结论是**不需要**，之前的判断错了。

### 实测

加时间戳追踪，普通键盘（悬浮关闭）下：

```
23:35:35.115 apply in=[六个原生 id] out=[theme, textediting, settings]
23:36:15.588 apply in=[theme, textediting, settings] out=[theme, textediting, settings]
```

第二次是改完设置再展开时的调用，**确实跑了**。再改一次（把单手打开）：

```
23:41:51.552 file=access_point_theme_setting:1|access_point_one_handed:1|...
23:41:51.554 apply in=[六个原生 id] out=[theme, one_handed, textediting, settings, ...]
```

顺手确认了两件事：

1. **文件读取是好的**：`path=/data/user/0/<pkg>/shared_prefs/floating_keyboard_preferences.xml
   exists=true`，读到的就是改后的值，没有跨进程缓存问题
2. **普通键盘展开会调 `a(Z)V`**：它和悬浮共用同一条渲染路径，`AccessPointsBar.a(List)` 的两个
   调用点分别在 `AccessPointsManager`（普通）和 `ahm`（悬浮 Delegate），我这个钩子挂在 manager
   那个上，两边都覆盖到了

### 那「只看到一个」到底是什么

是**残留状态**：改完设置后没有重新展开就直接看，工具栏还是上一次的结果。重启（或收起再展开）
之后就正常。换句话说当时那版包的问题不在读取和刷新时机，在那次操作没有触发重绘。

最终版实测：配置三个（主题、文本编辑、设置），普通键盘展开三个，关掉一个变两个，都即时生效。

### 一个无害的残留

`out` 里会带上 `access_point_search`、`access_point_sticker`——它们不在配置里，按「配置没提到
的保持原样」被保留了。但 `map` 里根本没有这两个键，渲染时会被跳过，所以不显示也不影响结果。
真想清掉得在 smali 里按 map 过滤，收益太小，先留着。

## 关掉能生效、打开回不来：白名单只删不加

用户实测报的：关掉「设置」→ 键盘上确实没了；再打开「设置」→ 还是只有两个。

### 两个 bug，叠在一起

**第一个**在 `apply` 的顺序重建里：

```java
for (String id : enabled) {
    if (ids.contains(id) && !result.contains(id)) result.add(id);   // 错
}
```

关掉某个入口时它已经被从前一份列表里删掉了，于是 `ids.contains(id)` 永远为 false，再打开时
加不回来。去掉这个检查就好——`map` 里没有的 id 渲染时会跳过，多带进去也无害。

**第二个**在收尾的白名单同步：

```java
known.removeAll(disabled);   // 只删
```

`AccessPointsManager` 用 `a:Set` 当白名单，`a(Z)V` 遍历 `a:List` 时逐项 `Set.contains`
过一遍，不在集合里的直接跳过。只删不加，被关掉的入口就算重新出现在顺序列表里，也会在这里
被滤掉。补上 `known.addAll(enabled)` 才对。

### 为什么之前会误判

第一版修复只改了顺序列表，`out` 里确实有 `settings` 了，看着像好了。但屏幕还是两个——因为
第二道白名单过滤把它拦住了。加时间戳追踪才看清：

```
in=[六个原生 id] file=...settings:1 out=[theme, textediting, settings, ...]
known=[theme, sticker, search, more_access_points, textediting]   ← 没有 settings
```

`out` 对、`known` 错，两边不一致。修好之后 `known` 里就有了，屏幕也对了。

### 现在的行为

重启、关掉、再打开，三种状态都对：三个 → 两个 → 三个，全都在展开时立刻生效。

## 浅色应用下卡片底部那条灰带

用户报的：悬浮键盘在浅色应用上，下方有一块不明阴影。

### 定位过程

先取样像素，把「阴影」和「阴影」区分开：

```
x=540 竖扫
1560 (250,250,250)   卡片白
1592 (238,238,238)   灰带   ← 问题
1616 (194,200,210)   手势条
1656 (238,237,246)   应用背景（带紫调）
```

灰带是**中性灰**，应用背景带**紫调**，两者不是一回事，所以灰带是键盘画的。再横扫看宽度：

```
y=1650: x=200..979 是 (238,238,238)，两侧是应用背景
```

宽度正好等于卡片宽度——说明它在**卡片内部**，不是窗口背景。给 `keyboard_area`
涂红验证：红只填在手势条那一小条，卡片主体仍是白的。结论是卡片主体被上层 View 盖住了，
**只有底部 reserved 的那条 gutter 露着 `keyboard_area` 自己的背景**。

### 根因

`keyboard_area` 的 `android:background="?BgKeyboardArea"` 是层列表矩形（浅色下算出来是
238 灰），而按键和卡片主体各自上色（250 白）。卡片缩进以后，底部那条给拖拽条预留的
gutter 落在涂色区域之外，于是露出这层底色——就是那条灰带。

### 改法

`applyInsets` 里把这一层的背景去掉：

```java
if (area != null) area.setBackground(null);
```

按键和 header 都自己上色，这层本来就不需要。改完两种主题都干净：
卡片白直接接应用背景，中间没有过渡色块。

### 顺带确认的

- 窗口背景不是原因。之前试过 `window.setBackgroundDrawable(TRANSPARENT)`，像素完全没变，
  已撤回。
- 卡片底部本来就是直角（改之前也是），不是这次引入的。

## 卡片自己带阴影

用户看过浅色那张图之后给了个更准的判断：那条灰带如果算键盘的阴影，那就留着，但悬浮的时候
得跟着卡片走，不能定在屏幕边上。

查下来屏幕边上那条和卡片下方那条是两回事：

- **两侧的深灰**（194 左右）是**窗口**的阴影。窗口是全屏的，所以它固定贴在屏幕边缘。
  对比过：关掉键盘时该处是普通背景，开着才有，确认来自键盘窗口。
- **卡片下方的浅灰**（238）是 `keyboard_area` 自己的背景层，跟着视图走。

### 改法

`decor.setElevation(0)` 试过，**去不掉窗口那条**，所以不再试图消掉它。改成给卡片本身上
elevation，让它有一份属于自己的阴影：

```java
area.setElevation(SHADOW_DP * density(area));   // SHADOW_DP = 6
```

这条阴影随卡片移动和缩放，不再固定在屏幕边。灰带保留，按用户的意思不动它。

### 留下的

窗口自带的那条边缘阴影去不掉（这一层不受 `decor` 的 elevation 控制）。它和卡片阴影同时
存在，浅色主题下看起来是外面一层淡的、里面一层贴卡片的，暂时按这个状态留着。

## 编辑态那三个按钮改用现成图标

用户指出编辑模式里「移动」左边那个重置按钮画得不对，怀疑是手绘的问题。查下来确实是。

### 原来错在哪

`FloatingKeyboardEdit.drawReset` 里箭头头是这么画的：

```java
path.moveTo(...);
path.lineTo(...);
path.lineTo(...);   // 没 close
canvas.drawPath(path, glyph);   // glyph 是 STROKE 画笔
```

三段折线 + 描边，渲染出来是两根散开的线，不是实心箭头；方向的算法也把箭头放到了右上，
看着像「刷新」而不是「恢复默认」。这类图形本来就有标准画法，自己算三角函数没必要。

### 改法

三个按钮全部换成 Material 的标准矢量图标，不再手绘：

- `patches/res/drawable/ic_floating_edit_reset.xml`：标准 `settings_backup_restore`，
  逆时针环 + 左侧箭头 + 中心圆点，和原生编辑按钮的图形一致
- `patches/res/drawable/ic_floating_edit_move.xml`：标准 `open_with` 四向箭头
- `patches/res/drawable/ic_floating_edit_done.xml`：标准对勾

代码侧删掉 `drawReset`、`drawMoveArrow`、`drawDone` 三个手绘方法，改成按名字取 drawable、
`setTint` 成主题色后按包围盒绘制。资源缺失时什么都不画，不会崩。

放在 `patches/res/drawable/` 下是因为 `apply_patches.py` 会把它整个复制进 `decoded/res`，
补丁可以从原始 APK 复现，符合仓库的既有做法。minSdk 是 23，`setTint` 和
`getDrawable(int)` 都可用。

### 上机验证的结果

设备接回来之后装包看过了，三个图标都对：

- **重置**：逆时针环 + 左侧实心箭头 + 中心圆点，和原生编辑按钮一致
- **移动**：标准四向箭头
- **完成**：对勾

第一版图标偏大，撑出了圆盘。改成圆盘直径的 1.12 倍（移动按钮 1.16 倍）之后贴合了。

有一点要说明：`adb input tap` **进不去编辑态**。注入的触摸到不了键盘窗口，双击胶囊没有任何
反应，长按拖动也一样。所以验证时临时加了一个读 `debug_edit` 偏好的自动进入钩子，验完已经
删除，`final6.apk` 的 dex 里查不到这个字符串。设备上那份 `debug_edit=true` 也顺手清掉了。

## 两件事：虚拟键上方的灰带 + 卡片四周的阴影

这两件被搅在一起走了好几轮弯路，记清楚区别：

- **灰带**是 bug：手机虚拟键（手势条）上方那条 `(238, 238, 238)`，宽度等于卡片
- **四周阴影**是后来用户要的效果：卡片浮起来要有点投影

之前几轮一直把「用户嫌边上没阴影」当成「用户嫌那条灰带」，去改 elevation、去自绘
环形阴影，改动全落在四周阴影上，灰带一直在。

### 灰带是怎么回来的

`dfda7f3` 修过它，用的是 `area.setBackground(null)`：卡片被 scale 之后，键盘区的
背景会画在 padding 之外，那条 gutter 露出的就是键盘区自己的表面色。

后来 `198d859`（「卡片自己带阴影」）把这一句换成了 `applyCardShadow(area)`，
灰带就跟着回来了。**加阴影不能把清背景那句删掉**。

### 现在的组合

两件事同时成立：

1. `applyScale` 里 `clearAreaBackground(area)` — 保留 `dfda7f3` 的做法，悬浮时清掉
   键盘区背景，`resetScale` 时用 `restoreAreaBackground` 还原
2. `applyInsets` 里 `ensureCardShadow(...)` — `FloatingCardShadow` 自绘一个 even-odd
   环形，只画卡片外面那圈，`translationZ(-1f)` 压在卡片下面

阴影之所以必须自绘：elevation 阴影跟着 **layout bounds** 走，而卡片是用 `setScale`
缩放的，bounds 还停在整窗尺寸，阴影会跑到屏幕边上。

环形路径中间是挖空的，所以卡片内部完全不受影响，header 的半透明底色也不会被染灰。

### 窗口 surface 阴影：已解决

那条从卡片下方垂到导航栏的暗带，是 **IME 窗口自己的 surface 阴影**。判定依据：键盘开/关
同位置对比，只有窗口边缘的像素变；窗口 frame 占满全屏，阴影画在窗口边缘内侧。

**解法：把窗口收到卡片大小，窗口跟着卡片走。** 现在已经做到屏幕边缘、卡片下方全部干净，
只剩卡片自己周围一圈阴影。

#### 三个必须同时做对的点

1. **窗口宽高收到卡片大小**，宽度 `baseAreaWidth * factor + outgrow`，高度按实测
   `cardOffsetInWindow(area)[1] + cardHeight + handleHeight + outgrow`。只收宽度的话，
   窗口底边阴影会在卡片下方形成一条横带。
2. **纵向定位整体交给窗口**，`translationY` 从纵向彻底移除。`applyPosition`、
   `onHandleTouch`、`handleEditDrag`、`settle`、缩放全部改走 `moveWindow`。
   半改会让位移翻倍，卡片飞到屏幕顶或被裁。
3. **所有几何都用实测值，不要推公式**：
   - `cardOffsetInWindow`：area 与 content view 的 `getLocationOnScreen` 之差，含缩放 pivot
   - `windowOriginShift`：content view 屏幕位置减 `LayoutParams.x/y`

#### 两个踩过的坐标坑

- **`WindowManager.LayoutParams.y` 不是绝对屏幕坐标**，它相对可用显示区域（状态栏以下）。
  直接当屏幕坐标用，所有位置都会低一个状态栏高度，手柄因此掉进导航栏。
- **`getLocationOnScreen` 返回的是缩放后的视觉顶角**。手柄位置要用「视觉顶 + 缩放后高度」，
  加未缩放高度会多出一个 `(1-scale)*areaHeight`，手柄被推到窗口外裁掉。

#### 系统栏高度要读导航栏 insets

`getRootWindowInsets()` 对 IME 窗口返回 0。`getMaximumWindowMetrics` 减
`getCurrentWindowMetrics` 的差值也**不准**（实测 92-98，真实导航栏 126）。正确做法：

```java
manager.getCurrentWindowMetrics().getWindowInsets()
        .getInsets(WindowInsets.Type.navigationBars()).bottom
```

`freeRange` 用屏幕尺寸并扣掉系统栏与手柄高度；`moveWindow` 再按真实几何 clamp，
保证手柄永远不会落到导航栏里——否则系统吃掉触摸，卡片拖不上来。

#### 验证结果

- 拖动：上拖、下拖、到底后再拖上来都正常
- 松手位置：手柄停在手指松开的位置（拖到 1300 就停在 1300）
- 输入：按 x/z 正常出候选，候选栏完整
- 阴影：屏幕边缘与卡片下方 `y=2000` 以后全是背景色 `(238,237,246)`

#### Gboard 参照的结论

提取并解包了 Gboard 18.6.3。它设窗口的地方（`nro.smali` 的 `l` 方法）里，
`width = display.getWidth()` 是**全屏宽**，`setBackgroundDrawable(new ColorDrawable(0))`
是透明背景。照抄这两样对阴影**都无效**：`null` 与 `ColorDrawable(0)` 结果一样，
窗口背景不是阴影来源。`surfaceInsets` 在 Gboard 里一次都没出现。

Gboard 没有这条暗带，靠的是窗口高度跟着卡片走，而不是什么特殊 API。

#### 阴影这条路线为什么封存

那条例带是 **IME 窗口的 surface 阴影**，只有缩窗口能去掉。但缩窗口就会撞上原生布局：

1. `keyboard_area` 是 `InputView` 内部子 view，原生每帧重置它的尺寸和缩放（抖动的根因）
2. `InputView` 里有个 **126 px 手势条占位 View**，窗口一缩它就把键盘区从 740 压到 614，
   底行被裁。设 `GONE` 会被原生 `onLayout` 重新显示
3. 原生键盘行高不随窗口缩放，纯窗口尺寸驱动会裁底行

这三点都已在视图树里实测确认，不是猜测。要继续做阴影，**必须先解决手势条占位 View**
（改 InputView 布局 XML 里那个 View 的高度，或 hook 原生设置它可见性的地方），
否则缩窗口永远会裁底行。
