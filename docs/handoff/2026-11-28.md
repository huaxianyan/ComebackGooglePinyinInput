# 2026-11-28 悬浮编辑模式收尾与胶囊取色

基线：`feat/floating-keyboard`，本轮构建 `work/floating-f-build/pill9.apk`（测试包名，未打标签）。

## 编辑模式的三个退出条件

编辑模式是悬浮专属状态，卡片被重建或键盘收起后必须退出，否则叠层会留在旧几何上。三条路径分别落在不同的钩子上：

| 触发 | 钩子 | 几何处理 |
| --- | --- | --- |
| 键盘收起 | `PinyinIME.onFinishInputView` | 位置可信，写入偏好 |
| 输入视图重建（换主题） | `GoogleInputMethodService.c()` | 位置不可信，退回上次保存的浮动位置 |
| 关闭悬浮 | `resetScale()` 与 `scheduleHandle` 的禁用分支 | 直接清空叠层、拖拽条、probe |

前两条用 `replace_once` 注入到 `scripts/apply_patches.py`；第三条原本已由 `resetScale()` 覆盖，本轮补的是 `scheduleHandle` 里发现设置已关时提前 `return` 而不清理的那处，改为调用 `dropFloatingChrome()`。

**窗口可见性不可用**：`onWindowVisibilityChanged` 在这套 IME 里不会因键盘收起而触发，曾按它实现过一次，实测无效，已删除，不要再走这条路。

**跨包调用必须 `public`**：`onKeyboardHidden()` / `onCardRebuilt()` 一度声明为包内可见，调用方在 `com.google.android.apps.inputmethod.libs.framework.core` 包，运行时直接 `IllegalAccessError` 导致输入法进程崩溃。凡是从原生包 smali 调用的入口都必须是 `public`。

## 编辑模式的重置图标

原来按钮里的「恢复默认」是 Canvas 手绘弧线，改为原生 `ic_key_reset_keyboard_material_dark_theme`（`0x7f020182`），`getDrawable` → `mutate()` → `setTint(accent)`，取不到资源时仍退回手绘。

尺寸是本轮踩过的地方：该 PNG 画布 175×175，**墨迹只占 42%**（74×63，四周有内边距）。要让墨迹等于原弧线直径（`0.84 × 按钮半径`，约 15.1 dp），绘制 bounds 必须给到**整个圆盘直径**（36 dp），`0.423 × 36 ≈ 15.2 dp`。按盘子半径的 52% 给会让墨迹只有约 7.9 dp，明显偏小。

## 胶囊取色

胶囊是悬浮卡片的拖拽条，原来固定 `0xFFC2C8D2`。目标是与「收起键盘」「简繁切换」同层的**墨色**一致。

结论与依据：

- `softkey_hide_keyboard`（`0x7f0f02b7`）、`softkey_enable_simplified_input`（`0x7f0f0276`）、`softkey_disable_simplified_input`（`0x7f0f022f`）在视图树里**解析为 null**，这一排是画布画的，`res/layout` 里也搜不到这些 id
- 同排可用的容器是 `header_area`（`0x7f0f004f`，`FrameLayout` 1080×105）；`access_points_bar` 通常是 0×0，遇到空行要继续尝试而不是直接返回
- 主键区的键是 `SoftKeyView`（删除键 `0x7f0f00b4` 为 161×155），但键的填充同样由画布绘制，按它的位置取样只会得到卡片底色
- 因此按 `header_area` 取色：把卡片画进位图，在带内 16×4 网格取样，众数当行底色，**离众数最远的颜色当墨色**，距离平方小于 `1600` 时判定没有墨色、保留默认灰

粉色主题实测：行底色 `F48FB1`、墨色 `(51,51,51)`、胶囊叠加空闲淡出后为 `(89,69,76)`。取行底色的版本因为与卡片太接近，看起来像没有胶囊。

缓存以 `area` 实例为键（`handleColorSource`），卡片重建或换主题会重新取；`removeHandle()` 会清掉缓存。


## 编辑模式改用原生界面（混合路线）

调查与探针见 `docs/research/floating-edit-overlay.md`。结论：原生 `KeyboardEditingViewHelper` 不能直接复用（它假设独占键盘几何，与卡片已有的缩放/位移叠加会瞬移），但**它的布局可以**。

实现：`FloatingKeyboardEditView` inflate 原生 `keyboard_editing` 布局（`0x7f04007b`），视觉全部来自主题资源；几何和手势仍由 `FloatingKeyboardCompat` 现有逻辑处理。叠层按 `visualRegion` 布局，蒙版只盖卡片。

探针验证出的硬约束：

- anchor 用 `keyboard_area`，不是 `keyboard_holder`
- 必须等一帧再弹（`decor.post`），否则 anchor 可见矩形为空
- `IMetrics` 用 `service.getMetrics()`，服务不直接实现该接口
- 角标触摸区是 `expand_keyboard_button_*`，顺序必须是左上、右上、右下、左下

实测：移动、四角缩放、恢复默认、确认全部正常，任意主题下按钮清晰可读。


## 分支整体复查与修复

对 `feat/floating-keyboard` 全量提交做了一次独立审查，修掉以下问题：

- **恢复默认只重置大小**：按用户要求，位置保留，当前与退出编辑后都不移动；重置时把当前位置按新缩放折算成比例重新存回偏好，不再写默认位置。
- **缩放边界坐标统一**：`handleEditScale` 里锚点与 decor 边界都换算到屏幕坐标再算剩余空间，消除状态栏偏移；空间不足时不再用 `MIN_SCALE` 把卡片顶出屏幕。
- **关闭悬浮恢复原生阴影**：首次清零前保存 `InputView` 原生 elevation，`resetScale()` 与 `dropFloatingChrome()` 恢复并移除自绘阴影及 pre-draw 监听。
- **待机淡出的恢复用直接赋值**：`view.animate().alpha(1f)` 在 insets 每帧重启，动画永远推进不到 1，卡片会一直停在中途 alpha。恢复统一走 `restoreOpaque()` / `setOpaque()`，取消动画后直接 `setAlpha(1f)`。这是「关掉淡出开关后卡片一直半透明」的真正原因，光靠调整判断顺序修不好。
- **收起/重建清理全部手势**：新增 `cancelGestures()`，取消编辑与长按定时器、清 `pendingDrag/armingEdit/dragging/scaling`；拖动中被打断时把当前位置持久化且不做停靠。
- **淡出偏好默认值统一**：IME 运行层改为 `false`，与 Compose 设置层一致。
- **空闲探针按 host + area 双条件复绑**：只按 host 判断会让 probe 在 `keyboard_area` 被替换后继续绑定旧视图。
- **删除死代码**：旧自绘编辑层 `FloatingKeyboardEdit`（java 与 smali）与 `accentColor`/`accentFromPixels`/`accentFromAttributes` 全部移除；`setFrameBounds(Rect)` 改为无参 `fitFrame()`；修正三处与实现不符的注释。

尚未处理（记入下一轮）：延迟任务持旧引用、编辑层多点触摸、`ACTION_CANCEL` 被当成抬起、底部 padding 全局缓存、可见性限流丢弃恢复请求、空闲探针收不到 `ACTION_UP`。


## 边界问题续修

- **延迟任务持旧引用**：`scheduleHandle` 执行前核对 `findKeyboardArea(decor) == area` 且已 attached。
- **底部 padding 基准**：`baseBottomPadding` 改为绑定到具体卡片（弱引用记录 owner），换卡片时重读。
- **`ACTION_CANCEL` 不当抬起**：独立分支，不执行停靠、只持久化位置；双击时间戳只在未发生拖拽的普通点击时更新。
- **可见性限流**：只丢弃同向重复请求，方向改变立即执行。早先加的 50 ms 延迟与 `isAttachedToWindow` 检查回退，它们会让隐藏请求丢失。
- **编辑层多点触摸**：`activePointer` 跟踪活动指针，第二根手指不接管手势，`CANCEL` 时补发 `finished`。
- **拖动中断**：`MOVE` 里 `range == null` 曾 `return false`，会让 View 放弃整个触摸流，手指没松也再收不到事件；改为 `return true`（本次不应用，保住手势）。

## 单手入口与悬浮互斥

设计上单手模式与悬浮互斥，所以悬浮时必须让单手入口消失，而不只是视觉隐藏。

先前按 contentDescription 匹配一直无效，原因是漏了真正的入口：工具栏那个入口的描述是 **`One handed mode`**（`one_handed_access_point_content_desc`），而匹配列表里只有 `left_handed_content_desc`、`right_handed_content_desc`、`expand_keyboard_content_desc`，三个都不是它。

改为走自家 access point 机制：`AccessPointsOrder.apply()` 在悬浮开启时把 `access_point_one_handed` 从入口列表与注册集合中摘掉，原生 bar 因此根本不创建该入口，也不污染用户的 `shortcuts` 设置，关闭悬浮自动恢复。contentDescription 兜底同时补齐。


## 快捷入口栏加自定义入口（悬浮开关）

调研见 `docs/research/access-point-entry.md`。

做法：`init_access_points` 数组里加一个 style，原生就会把它当内置入口注册、排序、渲染、
染色、描述；点击另注册一个 `IAccessPointFeatureHandler`，id 对上就翻转悬浮开关。

落地：

- `scripts/access_point_patches.py`：字符串、style、数组项、矢量图标
- `patches/java/.../FloatingAccessPointHandler.java`：点击处理，静态防重注册
- `scripts/generate_floating_keyboard_smali.py`：为 `AccessPointsManager` 生成编译用 stub
- `scripts/apply_patches.py`：在服务建好 manager 后注入注册调用

实测：图标与其它原生入口同风格同色（bar 会统一染色），点击可双向切换悬浮开关，
悬浮开启时单手入口仍被摘掉。

排查过程中的两个坑：bar 默认折叠成一个箭头，点开才是图标行；停靠键盘本身就不显示这一行。
验证入口是否生效要先确认 bar 形态，否则会误判。


补一个细节：原生只在点击它自己的展开按钮时收起 bar，普通入口点完不收起。悬浮开关是纯 toggle，
没有跳转或面板，所以点了没反馈。为此给 `AccessPointsManager` 注入公开桥接
`collapseAccessPoints()`（内部调包内私有的 `b(1)`），handler 翻转开关后调用。
