# 2026-09-30 逗号与句号显示开关：白屏事故与方案转向

> **最终结果：本需求已搁置。** 同日在「自定义布局框架」调研结束后，用户判定工程量超出预期，决定不做（含 JSON 自定义布局框架）。见文末「搁置」一节与 [搁置决策记录](../comma-period-toggle-shelved.md)。

## 事件

审计包 `com.google.android.inputmethod.pinyin.pairauto`（2.2.0 / 4520500）装机后，**除手写外的全部键盘布局白屏**，完全无法输入。用户指出后立即切回正式版 `compat` 恢复设备。

- 状态位掩码与位冲突的修复本身是成功的：掩码加宽到 `0x7ffffffffffffff`、句号位从 bit 56 挪到 bit 58 后，输入法**不再启动崩溃**，进程稳定存活，崩溃缓冲区无记录。
- 但键盘视图树构建失败，表现为白屏且**日志里没有任何异常**，属静默失败。

## 我的判断失误

我先看到键盘区域的空白，误读为「候选区为空 + 远程转发渲染延迟」，没有意识到是键盘本体未渲染。两次截图哈希相同被我当成「画面已稳定」，实际是白屏本身稳定。**教训**：对比截图时，必须与已知正常的基线（正式版键盘）逐项比对键位，不能只看「有没有变化」。

## 根因方向

白屏由新增的自定义 View `CommaPeriodToggleKeyView` 引入。它不是原版机制的一部分，是我为了让空格**独占**释放宽度而自造的。

事后复核 `SoftKeyView.a(SoftKeyDef)Z`（第 1309 行），原版机制本来就能满足需求：

- 映射到**真实键**时无条件 `setVisibility(0)`，**不看布局初值**；
- 映射到**空或 `softkey_empty`** 时恢复布局初值。

因此「布局声明 `visibility="gone"` + keymapping 状态位」是原版对语言切换键的既有做法，**不需要任何 Smali 新增类**。

## 转向：纯布局 + keymapping

用户要求在修复前先重新研究「像开关输入法切换键那样局部修改布局」。研究结论：

1. **可见性**：语言切换键的做法可直接照搬。布局声明 `gone`，开启时框架用真实键强制置可见，关闭时恢复 `gone`。
2. **权重**：`SoftKeyView` 全文件无 `LayoutParams`／`weight` 字样，没有任何框架钩子能按状态改权重。权重只能来自静态布局。
3. **语言键为什么能「只给空格」**：它与空格同处一个 `layout_weight="500"` 的容器内。它 gone 后容器内只剩空格，容器全部宽度归空格。这是结构约定，零代码。
4. **两个标点槽位的处境**：它们是顶层兄弟，不与空格同容器。gone 后释放的宽度按权重比例**摊给所有可见兄弟**，不只给空格。

手机版实测换算（总权重 1000）：

| 状态 | 空格 | 符号键 | 右上标点 | 回车 |
| --- | --- | --- | --- | --- |
| 都开（原版几何） | 500 | 150 | 100 | 150 |
| 隐藏逗号 | 555.6 | 166.7 | 111.1 | 166.7 |
| 隐藏两个 | 625 | 187.5 | 125 | 187.5 |

**能让空格独占的两条路都被否决**：调整布局结构会改变默认键宽比例；运行时改权重就是本轮白屏的做法。

**决定**：接受「空格与其余兄弟按比例分摊」。核心效果（空格变宽、标点键消失）成立，零 Smali 新增，与语言切换键同构，渲染风险最低。

## 搁置（同日 12:45）

在上述调研之后，用户又连续追问键盘布局的可扩展性（独立 APK 插件 → 产物归属 → 用户自定义键位 → JSON 自定义布局框架），最后判定**整体工期超出预期，决定同时废弃逗号句号开关与 JSON 布局框架**，留待将来更合适的路径。

**搁置时的关键补充结论**（用户追问「导入多个 JSON 是否要先预注册多套布局」得出）：

- 每套 JSON 自带独立 id 池 → 必须编译期预注册，数量锁死 → **伪框架**。
- 所有 JSON 共用同一池既有槽位 id（T+ fork 复用 `keyboard_prime_bottom.xml` 已证明 id 池跨布局共享）→ **无需预注册，数量不限**，JSON 只是「排列数据」。
- 代价是只能重排/调宽/隐藏既有键，**不能新增系统里没有的键**。这是结构性取舍。
