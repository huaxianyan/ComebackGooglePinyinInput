### 已完成

官方行为变更已按「仅影响 target 37 应用」与「影响所有应用」两类归集并逐条判定。静态审计在本次生成的原始 APK 干净解码树 `work/a17-audit/decoded/`（3264 个 smali）上完成。

唯一明确需要改动的是 `System.load()` 的 DCL-C 只读要求。原生库加载器（混淆名 `amd`）是三级回退链：`loadLibrary` 失败后尝试加载 `filesDir/temp_lib_<versionCode>/lib<name>.so`，再失败则从 `sourceDir` 解压 `.so` 到该目录再 `System.load()`。第三步写出的文件属主可写，target 37 下会抛 `UnsatisfiedLinkError`。正常路径下 `loadLibrary` 即成功（本项目刻意用 `useLegacyPackaging = true`），所以这是潜在风险。调用方 10 处，覆盖拼音、英文、HMM 手写与手势、delight4。

判定为不涉及或低风险的项及理由均写在调查文档，其中 static final 反射限制、`MessageQueue` 无锁实现、LAN 权限、ContactsProvider CP2 两项、大屏方向限制、隐式 URI 授权等均通过静态审计排除。CJKV IME 无障碍 API 属新增能力，按项目约定需独立分支与「默认关闭」例外流程，本轮只登记。

### Android 17 输入法切换器图标（新发现）

用户使用切换器时发现拼音条目前面只有一个方块剪影，而 Gboard 是可辨识的图标。放大截图确认：切换器会把子类型图标单色化并缩到约 24 dp。

- `res/xml/method.xml` 里唯一的子类型写着 `android:icon="@mipmap/app_icon"`，指向彩色键盘 PNG（144×144，键盘加青绿「拼」字徽章、透明底）。单色化后只剩「宽矩形叠窄矩形」的轮廓，就是用户看到的方块。
- Gboard 的做法是给每种语言配一个单色字形：日语是「あ」，简体中文是「拼」。把简体中文临时加入 Gboard 后实测确认，两者都只是单个单色字符，缩小后依然清晰。
- Google 语音输入没有子类型图标，切换器就只显示文字、不显示图标。
- 与 target 无关：`compat`（target 36）与 `target37test`（target 37）在切换器里表现一致。

修法照 Gboard：新增 `patches/res/drawable/ic_ime_subtype_pinyin.xml`，把 Noto Sans CJK SC 的「拼」字轮廓做成 24 dp 单色矢量（黑色填充，由系统着色）；`method.xml` 的 `android:icon` 改指它；`verify_target37.py` 增加断言，禁止子类型图标再指回 `@mipmap/app_icon`。为取参考临时加入 Gboard 的简体中文已移除，Gboard 恢复原状。

`method.xml` 有四个资源限定符变体：`res/xml/`、`res/xml-v19/`、`res/xml-television-v13/`、`res/xml-television-v19/`。资源按 API 级别解析，手机上实际加载的是 `xml-v19`，只改基础版不会生效——第一版就是这么漏掉的。四个都已改，门禁用 `res/xml*/method.xml` 通配断言。

**真机复验通过。**切换器里 `Target37 Audit` 显示「拼」字；同一张截图里未重建的 `谷歌拼音输入法`（target 36 compat 包）仍是方块剪影，构成天然的前后对比。截图存 `images/ime-switcher-subtype-icon.png`，当前为第三版。

尺寸与字重共校准三轮，每轮都先在设备上量、再改生成器参数。第一版字形填满 24 dp 视口，实测「拼」墨迹 52×52 px，Gboard 的「あ」24×25 px，约 2.1 倍；420 dpi 下 24 dp 合 63 px，20/24 × 63 = 52.5 px 与实测吻合。第二版内边距改 7（10 单位方框），尺寸对上，但笔画游程中位数只有 2 px，偏细。第三版内边距 6.5（11 单位方框）并加 0.5 单位同色描边——Noto Sans CJK 没有 Bold 字面，Android 自己也是靠 Skia 加宽轮廓合成 CJK 粗体，这里用矢量描边做同一件事。重建为 `2.1.7-target37.5`（versionCode 4520504）后复测：「拼」29×29 px、笔画游程中位数 4 px，比 Gboard 的 24×25 px 大 16%。

### 分支验收时修掉一个既有的编码坑

首次用隔离 ID 触发分支工作流（run `38221149119`）时构建直接失败：

`scripts/build_modern_settings_host.py` 的 `run()` 会把命令行原样回显，而 GitHub 的 Windows runner 给脚本的 stdout 是 cp1252，`--launcher-label` / `--ime-label` 里一旦有中文就崩。仓库文档给分支验收的示例标签恰恰是中文（`Google 拼音功能审计`），这个坑迟早会再踩。

### 复核 master 产物时发现门禁并未真正生效

按 `docs/build-and-release.md`「正式发布步骤」第 4 步复核 master 产物（run `38222400562`，artifact `11735541218`）时，把下载到的 APK 重新解码后逐个复跑工作流里的门禁，有 4 个失败。回查 CI 原始日志，**同样的报错在 CI 里也出现了，但那一步仍被判为 success**。

根因是 `pwsh` 的退出码语义。GitHub Actions 的 PowerShell 步骤只在脚本末尾取一次 `$LASTEXITCODE`，中间某条原生命令失败并不会抛异常。`build-release.yml` 的 `Decode and verify final APK` 一步里 21 条门禁调用全部没有 `if ($LASTEXITCODE -ne 0) { throw ... }` 守卫，只有紧随其后的 aapt2 那条有，所以这一步的实际判定者只是最后一条 `verify_stable_resource_ids.py`。工作流别处用了 34 处 `throw` 守卫，唯独这一块漏了。

CI 日志里确认失败的 4 条：

| 门禁 | CI 报错 | 性质 |
|---|---|---|
| `verify_md3.py` | `active guide launch gate is incomplete: ['if-eqz v0, :blocked']` | 解码归一化 |
| `verify_target35.py` | `Android 15 verifier requires targetSdkVersion 35+` | 门禁过期 |
| `verify_paired_punctuation.py` | `processor does not complete the \uff08\uff09 pair` | 解码归一化 |
| `verify_inline_autofill.py` | `FileNotFoundError: work\inline-autofill-synthetic-provider\libs\classes.jar` | 依赖缺失 |

后三类的具体成因：

- **解码归一化（2 条）**。apktool 反汇编会改写手写 smali 的表现形式。`verify_md3.py` 找的 `if-eqz v0, :blocked` 在最终 APK 里变成 `if-eqz v0, :cond_0`，baksmali 把自定义标签换成了 `:cond_0` / `:goto_0` 这类生成名；`verify_paired_punctuation.py` 找的 `const-string v0, "（"` 变成 `const-string v0, "\uff08"`，非 ASCII 字面量被转义。两处的语义其实都还在原位（`claimGuideLaunch` 仍在 `Lapy;->a` 之前，寄存器也仍是 `v0`），只是断言写死了源码树的表现形式，而工作流拿它去跑最终 APK 的解码树。
- **门禁过期（1 条）**。`verify_target35.py` 第 28 行的白名单写死 `(35, 36)`，target 从 36 提到 37 时没跟着改。`verify_target36.py` 用的是 `36+` 判定，所以没受影响。
- **依赖缺失（1 条）**。`verify_inline_autofill.py` 要 `work/inline-autofill-synthetic-provider/libs/classes.jar`，工作流里没有任何一步生成它，这条门禁在 CI 里从未真正编译过。本机残留的那个 33 KB jar 也不含 `androidx.annotation.RestrictTo`，且门禁的源码清单漏了 `patches/java/.../pinyin/ViewFrameRateCompat.java`（`HeaderMotionCoordinator.java` 已 import 它），所以本地同样过不去。

**这次发布不受影响**：失败的都是「门禁断言 vs 解码树表现形式」的错配，不是 APK 里的真实缺陷。同一轮里真正查 APK 内容的门禁——`verify_target31/33/34/36/37`、`verify_stable_resource_ids`（6633 个 legacy 资源 ID）、`test_header_platform`、`test_sensitive_clipboard_compat`、`test_rime_sync_protocol`、`verify_modern_settings_runtime` 以及签名、对齐、16 KiB ELF 审计——在 CI 和本地都是通过的。

但这意味着 `docs/build-and-release.md` 第 224 行「最终静态门禁」这一项当时没有实际约束力。已在 `fix/final-apk-gate-enforcement` 分支修掉，见下一节。

### 修复门禁守卫与失配断言

分支 `fix/final-apk-gate-enforcement`。工作流那一步改成把门禁放进一个数组逐条执行、逐条守卫，解码与 `verify_stable_resource_ids.py` 也各补一条守卫；这样以后新增门禁必须同时进数组，不可能再漏。

4 条门禁按「语义等价」重写，而不是放宽标准：

- `verify_target35.py` / `verify_target36.py`：把 `targetSdkVersion` 枚举改成解析后比较下限（`>= 35` / `>= 36`），下次提升 target 不会再静默失效。
- `verify_target35.py` 的布局断言：原来要求 `res/layout/ims_input_view.xml` 与 `res/layout-v21/ims_input_view.xml` **同时存在**。实测最终 APK 里其实是 `res/layout-v21/`（2420 字节），是 apktool 解码时把被 minSdk 23 覆盖的 `-v21`、`-v13` 限定符折叠掉了。改为 glob 出实际存在的手机变体（排除 `television`）逐个检查。
- `verify_md3.py`：两处标签名断言改为按语义判定。`if-eqz v0, :blocked` 改成匹配任意标签；`if-nez v0, :launched` 除了匹配分支，还要求 release 调用落在 fall-through 路径上（用目标标签的**位置**判断，而不是名字），所以跳转方向被反转仍会报错。
- `verify_paired_punctuation.py`：匹配前先归一化 `\uXXXX` 转义，寄存器号改为不敏感。候选路径那条从「标签名含 `stock`」改为「跳转目标是裸调 super、且不带 `commitText` / `offsetSelection`」——按行为识别回退分支，比按名字更结实。
- `verify_inline_autofill.py`：这条门禁在干净检出下**根本编译不了**——它要的 `work/inline-autofill-synthetic-provider/libs/classes.jar` 没有任何一步生成，`autofill-1.1.0.aar` 也不在仓库里（整个 `work/` 都被忽略），所以它在 CI 里从未真正跑过。改为按门禁自身已有的 stub 机制补齐编译面：`androidx.autofill.inline` 的 4 个类型（`InlineAutofillCompat` 只用到 6 处调用），以及只有 Smali 没有 Java 源的 `ViewFrameRateCompat`。这样门禁完全离线自足，不必往仓库塞第三方二进制（还涉及 Apache-2.0 署名），也不依赖 Maven 可用性。`androidx.annotation.RestrictTo` 确认只是**警告**，不影响退出码，未处理。

中途试过「从 AAR 解出 jar」的写法，本地能过、CI 立刻报 `FileNotFoundError: autofill-1.1.0.aar`——因为 AAR 同样不在仓库里。这条弯路本身也说明：门禁的输入必须能在干净检出下自给。

反向测试确认放宽后的断言仍有牙：反转 `if-nez`、删掉 release 调用、反转 hook 判空极性、把 androidx 调用改成不存在的方法，四者都正确报错。测试用的解码树与源码都已还原。

分支 CI（run `38234324732`）验证了守卫生效：日志里能看到其余门禁全部通过，`verify_inline_autofill` 失败时守卫按预期抛出 `Final APK gate failed: scripts/verify_inline_autofill.py ...`，而不再是被静默吞掉。同一次运行的 `Build signed official Compose Material 3 host` 曾因 Maven Central 返回 403 失败一次，重跑即通过，属 runner 侧瞬时问题。
