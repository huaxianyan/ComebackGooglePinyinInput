# 组合候选的 Viterbi 解码契约

本阶段固定原组合器使用的解码契约与增量证据，尚未实现宿主 Viterbi 解码器。已有接纳器继续读取实际已选记录，不把本文的静态关系写成已完成的路径生成。接纳与 scale 见 [扩展状态](key-expansion-state.md#已选路径的接纳与结果集合)。

原诊断明确指向 `i18n/input/engine/lib/viterbi/viterbi_decoder_impl.h`。因此可称为 Viterbi 路径，不根据这个文件名猜完整 C++ 类型。

## 原组合器的固定配置

`0x190c44` 建立一个解码器，配置原字依次为 `20/0/0`，末字节为零。`0x190b68` 在首字非零时分配实际状态，首字为零时不分配。本研究配置为 20，不能据此把未支持的模型当作空解码器。

状态中 `+0x04` 保存该数量参数，`+0x08` 保存第二个原字，`+0x0c` 保存第三个原字。`+0x10` 按末字节选择零或首字。当前额外加项、阈值及该分支参数均为零，字段原名仍未恢复。

组合用模型地址点为 `0x67a1f0`，回调已确认：

| slot | RVA | 实际行为 |
| --- | --- | --- |
| 2 | `0x18eae8` | 从上下文首个实际选择读取 `+0x20` 分数，以 S0 返回 |
| 3 | `0x18eaf8` | 返回 20 |
| 4 | `0x18eb00` | 返回 true |
| 5 | `0x18eb08` | 返回零 |
| 6 | `0x18eb10` | 返回 false |
| 7 | `0x18eb18` | 返回一 |
| 8 | `0x18eb20` | 返回 false |

`0x190818` 读取 slot 7 更新状态 `+0`，并将两个上下文参数设为该值减一。slot 6 决定另一种有状态路径，当前模型为 false。上述常量来自实际回调，不是测试替身。

Ghidra 将 `0x18eae8` 显示成 undefined4 返回值，实际指令是 `ldr s0, [x0, #0x20]`。后续移植必须保留 float 返回，不能按伪码改成整数转换。

## 顶点与提交

状态 `+0x20`、`+0x38` 分别持有两组顶点指针，`+0x50` 记录已到达位置。每个顶点分配 `0x68` 字节，已观察部分为：

- `+0` 是可读状态标志。
- `+0x08`、`+0x38` 是两组连接容器。
- 两个容器分别在顶点 `+0x28`、`+0x58` 保存数量参数。
- 连接记录步长 `0x20`，包含当前选择指针、前驱连接指针和 `+0x10` 的 binary32 分数。其余字段尚不作为新宿主协议。

`0x190a24` 为位置零建立顶点，给首组初始化数量一。种子连接的选择、前驱和分数均为零，随后按原流程完成顶点收尾。它是路径起点，不能把它作为输出中的空 token。

提交由 `0x191284` 进入 `0x190fd8`。原实现只处理起点小于终点的范围，按需扩展两组顶点。它准备起点的连接，再在连接非空时进入实际转移。正常组合路径调用 `0x18f270`，另一种有状态实现为 `0x18f044`，后者不在本阶段范围。

`0x18f270` 先读取模型 slot 8，选择目标顶点组。当前模型返回 false，使用第一组。转移保存实际选择和前驱连接，由模型读取当前选择分数。

路径累加使用普通 binary32 加法，不调用 AddLogScores。首个前驱的形状是先加前驱分数与边分数，再加配置项。后续前驱先加边分数与前驱分数，再加配置项。当前配置项为零，仍不改成 double 归约或重算整个指针列表。

后续前驱是否重算模型分数，还依赖 `0x13a48c` 的上下文比较。这个公共比较尚未展开，不能因当前模型只读取一条边就删掉原判断。

## 有界连接与同分顺序

`0x13d78c` 插入连接。它维护数量参数加一的物理存储和一个堆状态标志，不等于简单的「追加后稳定排序，取前 20 项」。达到边界后执行原建堆、首尾交换及下沉流程，后续仅在堆顶分数严格小于新分数时替换。

这里要区分物理记录数和 `0x13a9ec` 返回的可读数量。该大小助手、建堆 `0x139724` 和下沉 `0x1397c8` 尚未恢复为宿主源码，不能把物理数量直接当作候选数量。

顶点收尾 `0x140480` 先调用 `0x191a8c` 准备连接，再以 `0x13ff4c` 整理可读记录，非空时才设置可读标志。准备及整理步骤仍需展开，不能把置标志当成完整收尾。

最终输出另用 `0x13f190` 按分数降序整理。该实现按记录数分派小规模排序、插入和分区路径，比较只有分数，没有附加 ID 次序。当前真实资源包含同分项，因此不能补一个 ID 次序，也不能直接假定宿主 `std::sort` 或稳定排序具有相同保留顺序。

结果接纳同键保留首次记录。若解码顺序被替换，即使最后仍按 ID 输出，也可能保留不同的 scale、文本或标记。这是移植原连接顺序的实际理由，不以排序后看起来一致代替验收。

## 路径提取与回溯

公开入口 `0x1905b8` 先清空输出，再经 slot 8 进入 `0x19152c`。后者在实际状态非空时进入 `0x191294`。

`0x191294` 要求请求位置非零且已到达。它检查两组顶点的可读状态，累计可读连接数，并以配置数量限制本次输出。先把两组连接加入临时有界容器，再由 `0x13f190` 整理。

内部提取向已有输出追加，和公开入口的清空不同。输出记录步长 `0x20`，首字保存已选连接的实际路径分数，`+4` 写零，`+8` 起是实际选择指针向量。接纳器读取的正是这份分数和指针列表，不在接纳阶段重新求和。

`0x18ffd0` 先递归访问有实际选择的前驱，再追加当前选择。种子的选择为空，因此不会输出种子。这个顺序保留路径中的边顺序，不反转指针列表。

连接中的前驱是实际记录地址。宿主移植必须先明确连接容器完成后何时保持稳定，不能在容器可能重分配时借用元素地址，再靠重跑测试掩盖生命周期问题。选择指针也借用原组，需保持到路径接纳完成。现有 LearningKeyResultSet 在接纳时取得字符串快照。

## 证据与下一步

新增 19 段完整 FDE，均与原版及保留 v2.1.7 库 raw-equal。中央从 532 增至 551，旧区域直接沿用。增量记录为：


成功 Ghidra 导出位于 `expanded-key-decoder-entry/`、`expanded-key-viterbi-core/` 和 `expanded-key-viterbi-order-verified/`。组合器、位置收尾和已选路径接纳的旧证据继续沿用，不重复导出。

本轮没有产品实现改动，没有运行宿主构建、原 ARM 或 Android。静态关系不等于路径顺序、剪枝、同分结果或性能已通过运行验收。原范围错误诊断、非当前配置、有状态模型、OOM 和完整候选生命周期仍未恢复。

下一步先展开 `0x191a8c`、`0x13a9ec`、`0x13a48c` 与 `0x13ff4c`，闭合可读数量、上下文、准备和整理语义，再沿 `0x139724/0x1397c8` 恢复有界容器。同分保留与前驱稳定后，再接现有接纳及 scale 消费。

取证时曾把 Ghidra 显示地址误作 RVA，原始失败日志已保留。显示 `0023d78c` 对应 RVA `0x13d78c`。失败脚本还会留下输出目录，修正后改用新的 verified 目录。Headless 进程退出零不代表脚本成功，实际脚本错误和缺失输出均未计作成功证据。
