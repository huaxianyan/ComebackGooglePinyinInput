# 写编辑器的游标与引用缓冲

已把写编辑器自己的精确匹配游标和引用缓冲接入现有更新、插入与范围发布。读取游标与写入游标分开持有，继续共用同一查找、引用编码及固定记录编辑。

## 原持有与调用顺序

原 `0x1de788` 在编辑器构造时保存父对象、底层 editor、kind 零游标，并初始化 `+0x20` 的空引用缓冲。游标与缓冲持续到编辑器释放，不在每次调用时重新创建。

`0x1ded68` 的更新顺序为：

1. Reset 自己的游标，再 Append 完整 key。
2. 路径成功且存在精确结果时，将缓存引用复制到同一引用缓冲。
3. 按引用定位实际记录，仅更新该记录，失败不创建 key。

引用复制沿原 `0x1d630c` 的状态语义：忽略复制状态，由后续引用长度与记录校验决定更新结果。不把它改成额外失败门禁。

`0x1dec04` 的插入先通过原 slot 1 尝试更新。任何 false 都进入追加分支，`0x1deb4c` 先追加值，再把引用写回同一缓冲，最后调用底层 key 插入。key 准入失败保留先前追加的记录，成功更新既有 key 则不改调用方端点 ID。

## 宿主实现

[trie_value_editor.h](../../research/native-rewrite/recovered/trie_value_editor.h) 的 TrieValueEditor 直接持有同一 TrieExactMatchCursor 和 OwnedByteRegion reference。两者初始为空，没有 readiness 字段、虚句柄或转发方法。

- 原 UpdateTrieValueByKey、InsertTrieValue 保留唯一实现，显式接收实际编辑器状态。
- 更新复用自己的游标和引用缓冲；插入的回退追加继续使用同一个缓冲，不清空前一阶段状态。
- CopyReference 表达原忽略复制状态的协议，读取和写入复用同一引用编码，不复制另一套四字节算法。
- SingleTrie 协调器持有一个 value_editor，六子模型两个方向各持有自己的 value_editor，与已有 key_cursor 分开。
- 范围发布显式传入同一个写编辑器。非空范围更新走该状态，空范围仍直接删除端点，保留原次序与失败差异。

旧函数签名已移除，所有真实调用方同步迁移。没有兼容重载或逐方法转发类，也没有把存储参数收进新的假父对象。

状态不保留临时 DATrieView。调用方保持同一存储独占，每次操作提供当前视图；更新先 Reset 游标，再按当前结构查找，沿用 COW 后重建视图规则。

## 验证

使用原写编辑器模块的同一实际流程和字面预期，没有追加平行 fixture 或防御性测试：

- 新 key 追加实际值并发布端点，连续两次更新既有 key 保留 ID、key 数与记录数。
- 排除字节的 key 在准入失败前已追加值，该记录仍保留。
- 较长 key 与前缀共存；删除、裁剪后继续插入，端点复用、实际值和保留副本保持。

全源码严格编译一次。写编辑器模块、SingleTrie 完整流程、六子模型完整流程均通过。另两个迁移调用方只编译链接，不重复执行已验证能力。

七份 SingleTrie 文件、六子模型临时文件及两份 generation 导出在同一次流程中精确清理。对象、archive 和五个二进制随后清理；生成源码和 build.log 留存于 `work/native-rewrite/value-editor-state-build/`。

本轮没有新增 native 区域，直接复用既有构造、更新、插入、追加和引用复制证据。中央保持 `358` 区域，不重跑已通过的字节比较或中央导出。

## 尚未覆盖

这是实际编辑状态的持有恢复，不是原虚 editor 获取工厂。原父对象及子句柄仍以调用方提供的同一存储和当前视图表示，未恢复虚句柄 ABI、获取失败与引用计数释放路径。

全部 OOM、旧引用在分配失败时的残留、原分配次数、并发和性能未完整验收，不以顺利路径通过代替失败等价。未执行原 ARM64，未操作设备、正式包或用户词典。

下一步恢复实际下层对象获取与释放，保留原两对象都尝试获取、再一起判空的顺序，并接模型锁及 accessor 生命周期。
