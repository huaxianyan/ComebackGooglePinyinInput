# 源码重建调查状态与构建缺口

## 当前结论

当前尚未达到完整调查结束或独立源码输入法就绪的条件。本轮已恢复旧研究、补齐 `v2.1.7` 功能基线，并推进 JNI、C++ 类型和 composing 消费边界。没有把反编译产物整理进一个目录就称为源码工程。

目前仍缺 native 搜索、排序、学习、滑行和手写的完整实现规格与可编译源码。完整的输入生命周期及各模式状态机也未全部闭合。原始库里的类型、接口和调用关系已经比旧研究清楚，但不能用这些元数据代替算法。

目标与最终验收只维护在 [研究计划](../native-rewrite-plan.md)。功能状态只维护在 [功能清单](feature-inventory.md)，ABI 证据见 [JNI 与 C++ 边界](native-abi-map.md)。

## 各层应如何进入源码工程

| 层 | 当前材料 | 源码重建的工作 |
| --- | --- | --- |
| 设置、引导、主题编辑与恢复 | `modern-settings/compose-runtime/src/` 中已有 Kotlin 源码 | 直接整合，替换依赖旧混淆类、反射和分离 DEX 的连接点，保留偏好与业务契约 |
| Header、Clipboard、Inline Autofill | `patches/java/` 与 `headerplatform/` | 直接编译现有业务代码，替换 Smali 宿主连接，保留 Candidate 与远端 Surface 的不同所有权 |
| 备份、Rime、状态与自动任务 | `patches/java/` 与 `rimesync/` | 复用业务规则，重建真实词典访问端，保留 SAF、准入和后台恢复语义 |
| 复古 9 键、成对标点、主题及平台补丁 | Java、Smali、资源、生成器和对应门禁 | 按实际职责迁入输入状态与 UI 实现，不保留另一条补丁构建轨道 |
| IME、键盘、候选、触摸与模式状态 | 原始 DEX、资源与当前补丁 | 从真实入口恢复可读的会话、事件与状态，不机械照搬混淆类层级 |
| 拼音、英文、滑行与手写执行逻辑 | 原闭源执行库及新增 ABI 证据 | 恢复类型、算法和状态的源码实现，旧执行库只能作研究对照或明确标注的过渡 |
| 词典、模型、主题包与资源 | 原始二进制数据及部分格式研究 | 明确来源、格式、读取器与打包方式，保持持久数据兼容，不要求把所有数据强行转成文本 |
| 常规第三方依赖 | AndroidX 等已有依赖及 native 中待分离的通用代码 | 核对来源、版本与许可，使用可获取源码的正式依赖，不把通用依赖全部认成需要自写的业务 |

这是责任层划分，不是已经冻结的 Gradle 模块图。未确认的调用关系不先用接口、空实现或返回固定值填上。

## Java 源码不是 DEX 的逐类转写

固定原始 DEX 排除 bridge 标记方法后，仍有 925 组仅返回类型不同的方法重载，涉及 575 个类。这是源码形状风险盘点，不等于这些方法全部需要手写或重命名。部分编译器产物可以由源码重新生成。

一个明确的例子是 `axo` 中同时存在：

```text
a()Lbrj;
a()V
a()Ljava/lang/String;
```

这些不能直接成为同一个 Java 类里的三个 `a()` 声明。同名异类型字段也需要处理。恢复可读源码要建立 DEX 身份到语义名称的映射，再更新真实调用方，不能只依赖反编译器生成数字后缀。

已有可读 Kotlin/Java 不重新抄写。反编译器成功输出一段 Java，也不代表控制流、泛型、反射和资源关系已经可以正确编译与运行。

## 最终构建必须真正替换的部分

常规 Gradle/Android 工程应直接编译 Android 源码，必要时通过 NDK/CMake 编译 native 源码。当前宿主流程中的以下步骤不属于最终构建：

- 从原始 APK 解码并取得执行代码。
- 生成、修改和组装 Smali，再与独立 Compose DEX 拼接。
- 在构建时运行反编译器，或把反编译结果当临时源码生成器。
- 继续把原核心执行库作为已经重建完成的黑箱引擎。

单独使用 Gradle 生成了一个 APK，不足以证明这些依赖已经消除。最终应在干净 checkout 中沿正常构建图检查真实输入，再验证实际 APK 的代码、行为和迁移。

资源和持久数据需要单独处理。当前资源 ID、主题包、词典权重、原生合并和已有升级身份不能随模块迁移而悄悄失效。采用新的内部结构，不等于获准改变用户可见语义。

## 分析环境与授权边界

本轮复用已有 Windows JDK 17、apktool 2.12.1，以及既有 WSL 的 GNU demangler。没有安装工具，也没有改用户配置、系统配置或 MCP 注册。

现有条件仍有明确缺口：

- 当前 Windows Python 未安装旧研究要求的三个分析依赖，固定版本见 `research/native-rewrite/requirements.txt`。
- 既有 Ubuntu 默认 Python 为 3.6.8。已有 objdump 的目标列表不包含 AArch64，Node、Java 和 Ghidra 不在本轮检查到的 PATH 中，不能把该环境写成 REA 已就绪。
- REA 官方 Windows Ghidra 接口不接纳本项目的 ARM64 ELF。它的 Android/JADX 能力可以另行评估，但不能把这一接口当作 native 核心已经有完整后端。
- 本轮的局部 ARM64 常量识别器只服务取证，不扩展成自制完整反编译器。未识别指令会终止该块的常量追踪，空结果不证明不存在调用。

最小的下一步环境需求，是在既有共用 Python 中恢复声明的分析依赖，继续使用旧研究的真实反汇编与数据读取入口。已只读查询 PyPI 元数据，三个固定版本均提供 CPython 3.12 / Windows x64 可用的 wheel，尚未下载或安装。

后续是否部署完整 native 反编译后端，再按实际缺口选择。工具安装需单独授权，本轮未把「继续调查」扩成系统改造权限。

## 仍未关闭的研究问题

1. 扩展结果怎样进入搜索、评分、剪枝、长句与最终候选，哪些参数受设置和模式影响。
2. 用户词典编码、学习、衰减、权重与持久化的完整语义，及未解析的模型辅助数据。
3. 英文、滑行、笔画和手写各自的状态与模型协议，不能以全拼或 JNI 覆盖代表已经完成。
4. `WordRecognizerJNI` 的重复 export 实际如何装载和绑定，静态 loader 别名证据不代替运行时确认。
5. 生命周期、光标、部分提交、触摸取消和各字段模式的完整行为规格。
6. 原始或派生代码、模型与资源的分发边界。`NOTICE` 没有把整个仓库或 `research/` 自动纳入 MPL，本轮不扩大许可范围。

这些都是未完成项。没有新增真机、Root、私有数据导出、正式安装或发布授权时，继续做能在本地固定输入上完成的研究，不借历史授权补做设备实验。
