# 逗号句号开关：项目搁置决策记录

> 日期：2026-09-30
> 状态：**已搁置（SHELVED）**，非放弃。等待更合适的实现路径。

## 一、决定

用户决定**同时废弃以下两项**：

1. **底部行逗号/句号独立显示开关**（原始需求）
2. **用户自定义键盘布局 / JSON 导入框架**（调研中派生的需求）

理由（用户原话）：**「太复杂了，有点超出我预想的工期」**。

这是一个正确的决定——收益与工程量严重不成比例，且方向存在结构性障碍（见下）。

## 二、为什么搁置：两个需求的真实成本

### 需求 1：逗号/句号独立开关

**表面**：给两个键加个 `visibility` 开关。

**实际**：原版布局在编译期固化，`SoftKeyView` 对 `LayoutParams`/`weight` 引用数为 **0**，键盘视图路径上**无任何 addView/removeView**。想让逗号 gone 之后空格变宽，唯一手段是运行期改权重——**而这正是白屏事故的成因**。

纯布局方案（方案 B：按权重比例分摊）虽然零 Smali，但效果是「所有可见键同比例微增」，不是用户期望的「空格独占变宽」。**这是一个效果妥协，价值打折。**

### 需求 2：用户自定义布局 / JSON 框架

**表面**：加个 JSON 解析。

**实际**：是新子系统，需同时就位三套东西（视图树 / 映射表 / 软键定义），且：

- 槽位 id 是编译期资源 id，运行期造不出来 → 只能复用既有 id 池
- 想支持任意多 JSON，就必须**共用 id 池**；一旦某套布局要造新键，就退回「预注册有限套数」
- 原版加载链是为编译期设计的（`inflate(resId)` 一次成型 + 按 resId 缓存），要绕过只能在 `bbc` inflater 上拦截
- 还要配套：文件选择器、存储目录、列表 UI、导入/启用/隐藏/删除、坏 JSON 兜底

**结论**：技术可行，但工程量是「新子系统」级，与「加个开关」的原始需求相差两个数量级。

## 三、白屏事故的遗留教训（重要，不可忘）

审计包 `pairauto`（2.2.0）装机后**除手写外全部键盘布局白屏**，完全不可用。进程稳定存活、崩溃缓冲区无记录、**日志无任何异常**。

**根因**：自造的自定义 View `CommaPeriodToggleKeyView`。

**关键教训**：
1. **看截图不能只看「有无变化」，要逐项比对已知正常基线。** 当时两次截图哈希相同被我误读为「画面稳定」，实际是渲染失败。
2. 自定义 KeyView 子类**不是绝对禁区**，但门槛在「继承 `SoftKeyView` + 生成脚本 + 静态门禁 + 设备验证」四件套都齐（T+ fork 的 `SimplifiedTraditionalToggleKeyView` 是正面例子）。
3. **静态门禁比人眼截图可靠。** 本项目已吃过一次亏。

## 四、将来可能的更好路径（留给未来的自己）

以下路径按「工程量 / 可行性」排序，供重新启动时参考。

### 路径 1：T+ 式「新增一整套静态布局」（成本最低，已验证）

参考 [Tback-google-pinyin-input](https://github.com/JunperoH/Tback-google-pinyin-input)：
- 新增整套布局 = 几十个 XML 文件，**不改 `KeyboardViewDef`、不加状态位、不重写 inflate**
- 脚本化生成，有完整门禁与验证矩阵
- 局限：用户只能**选**，不能改

**适用**：如果只是想多一套键位方案，这是最快路径。

### 路径 2：共用 id 池的「重排引擎」（中等成本，中间形态）

- 不发明新 id，只在**既有槽位之间**允许用户搬动位置、调宽度、隐藏
- 因为只搬不造：不需要预注册、不膨胀、不占状态位
- JSON 只是「排列数据」，数量不受限

**适用**：用户确实要「自己排布键位」时的可行子集。**注意这是 JSON 框架的可落地版本，而非全功能版。**

### 路径 3：「逗号句号开关」换个切口（待发掘）

当前障碍是「想让空格独占变宽，必须运行期改权重」。

可能的替代思路（均未验证）：
- **改布局结构**：把逗号/句号移进与空格同一个 `LinearLayout` 容器（仿语言切换键的做法）——但这会**偏移默认键宽比例**，需评估是否可接受
- **新增专用布局**：像 T+ 那样新增两套底部行布局（「都显示版」和「都隐藏版」），用户切换的是**布局**而不是开关——避开运行期改权重
- **接受妥协**：就用方案 B（按比例分摊），零风险

### 路径 4：独立 APK 插件（已证不可行）

跨 APK 资源表是 AssetManager 层安全边界，加权限也绕不过。`ang`/`Lang` 只是同 APK 内双包名回退。**别再走这条。**
